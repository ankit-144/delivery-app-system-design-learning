# 3.2 — A Redis lock that expires under its holder

> **Phase 3: scale out.** Distributed locks are harder than they look. This is the failure that
> fencing tokens exist for.

## How the Redis lock works

[`RedisLock.java`](../../services/core-service/src/main/java/dev/quickdrop/core/redis/RedisLock.java):

```
acquire:  SET lock:stock:1 <random token> NX PX 2000     only if nobody holds it; disappears after 2 s
release:  if GET lock:stock:1 == <my token> then DEL     never delete a lock someone else now holds
```

Both are Lua scripts, so each runs atomically inside Redis. Two details matter:

- **The TTL** (`PX 2000`). If a holder crashes, the lock frees itself instead of blocking the store
  forever.
- **The random token.** Without it, a slow holder could finish *after* its lock expired and delete the
  **next** holder's lock, which would let a third one in.

`make load ID=3.2 MODE=no-pause` shows it working: 0 oversold.

## Story

A Java process freezes now and then: a stop-the-world GC pause, the VM being descheduled by the
hypervisor, a swap storm. A pause of a few seconds is rare but real. Here, **5% of lock holders freeze
for 3 s** right between reading the stock and writing it. The lock's TTL is 2 s.

## Run it

```bash
make load ID=3.2 MODE=broken
```
```
FAIL oversold_units         violations=249
holders that froze: 31
locks that expired before release: 31
```

31 short pauses, 249 units sold that didn't exist.

## Why

```
 holder A (core-1)                      holder B (core-2)
 SET NX → got lock (fence 41)
 read stock = 120
 ……… frozen 3 s (GC) ………
        lock expires at 2 s ──────────▶  SET NX → got lock (fence 42)
                                          read 120, write 119, … sells 60 units in 1 s
                                          release
 wakes up, writes stock = 119          ← overwrites everything B sold
 release → "not my lock anymore"  (expired_before_release)
```

From A's point of view nothing happened: it never saw an error, and **a process can't notice its own
pause**. Any check like "do I still hold the lock?" can be followed by a pause before the next line runs.

Meanwhile 60 customers have paid for units that A just put back on the shelf. That's why 31 pauses
cost 249 units.

Making the TTL longer only makes the window rarer, and it makes a crashed holder block the store for
longer. There's no TTL that is both safe and live.

## Fix: fencing tokens

```bash
make load ID=3.2 MODE=fixed
```
```
OK   oversold_units         violations=0
holders that froze: 21
locks that expired before release: 21
writes refused by fencing (lock_lost): 19
```

The acquire script also runs `INCR fence:stock:1`, so every holder gets a number higher than all
before it. Every write carries that number, and **the database** refuses old ones
([`InventoryDao.setQuantityFenced`](../../services/core-service/src/main/java/dev/quickdrop/core/inventory/InventoryDao.java),
migration `V4__inventory_fence_token.sql`):

```sql
UPDATE inventory SET quantity = ?, fence_token = ?
WHERE store_id = ? AND product_id = ? AND fence_token < ?      -- my token must be newer than the last writer's
```

A wakes up with token 41, B already wrote with 42, A's update matches 0 rows, and the order fails with
`lock_lost` (HTTP 409). The customer retries instead of getting phantom stock.

The fencing check runs in the **resource being protected**, not in the lock service. The lock becomes
an optimisation: it keeps holders from colliding most of the time, while the database guarantees
correctness all of the time.

## The bigger picture

This is the core of the well-known Martin Kleppmann vs. Redis "Redlock" debate:

- A lock with a lease (TTL) can never guarantee mutual exclusion against pauses and clock problems.
- If correctness matters, you need fencing at the storage layer, or a storage layer that does the
  check-and-write itself (1.1's atomic `UPDATE`, which needs no lock at all).
- Redlock (locking on a majority of 5 independent Redis nodes) protects against a *Redis node* failing,
  not against a *client* pausing. It doesn't solve this scenario.

Use a distributed lock **for efficiency** ("don't let two workers do the same expensive job"), not
**for correctness** ("never sell a unit twice"). See also the Redis replication failover entry in the
FAILURE_TRACKER: an asynchronous replica can lose a lock that was just granted.

## Also notice

**Average latency was ~7 s in the broken run.** One lock per store serialises *every* order for that
store across all instances, and every frozen holder stalls the store for 2 s. Locks are a throughput
ceiling as well as a correctness tool.
