# 1.5 — Optimistic locking on a hot item

> **Phase 1: correctness under concurrency.** All three strategies here are *correct*. This one
> is about cost.

## Story

A viral product: plenty of stock, but every customer wants that same product. 150 orders per
second, all touching **one inventory row**.

## Run it

```bash
make load ID=1.5 MODE=optimistic
make load ID=1.5 MODE=pessimistic
make load ID=1.5 MODE=fixed          # atomic UPDATE
```

`per-line-delay-ms=5`: each order does 5 ms of work while its row is locked. Add the rest of the
transaction and each order holds the row for ~6.5 ms, so **the row can serve at most ~155 orders/s,
whatever the strategy**. 150/s is just under that ceiling. The question is what each strategy
does with the queue.

What we measured (45 s each):

| Strategy | Avg latency | p95 | Version conflicts | Completed |
|---|---|---|---|---|
| optimistic | **3.66 s** | **4.97 s** | **4,379** | 5,214 of 6,751 (k6 ran out of users) |
| pessimistic | 6.85 ms | 7.4 ms | 0 | 6,751 |
| atomic | 6.79 ms | 7.3 ms | 0 | 6,751 |

## Observe

Sampled from the dashboards halfway through the optimistic run:

| Panel | Value | Meaning |
|---|---|---|
| Overview → Orders per second | **~90/s** | 150/s arrive, so the backlog grows by 60 every second |
| `rate(quickdrop_inventory_conflicts_total[20s])` | **~90/s** | every order conflicts about once: it reads, computes and writes twice |
| Saturation → DB connections | 10/10 active, 40 threads waiting | the pool is exhausted… |
| Postgres → Active connections by wait type | **9 × Lock**, 1 × none | …by connections queued on the one hot row |
| Containers → CPU | core 0.16, postgres 0.11 cores | nobody is working hard: everything is *waiting* |
| Saturation → Busy threads vs max | 50/50 | Tomcat is full, so new requests queue before they even start |

Pessimistic and atomic at the same moment: ~150 orders/s served, every connection doing useful work.

## Why

[`OptimisticReservation.java`](../../services/core-service/src/main/java/dev/quickdrop/core/inventory/strategy/OptimisticReservation.java):

```
read (quantity=500, version=17)
… think …
UPDATE … SET quantity=499, version=18 WHERE … AND version = 17     → 0 rows? re-read and try again
```

"Optimistic" means betting that nobody else touches the row in between. On a hot row you always
lose the bet, and losing is more expensive than it looks:

1. A dozen requests have all read version 17. One wins the `UPDATE` and holds the row lock until it
   commits.
2. The others' `UPDATE`s **queue on that row lock**. When the winner commits, each re-checks
   `version = 17`, finds 18, updates nothing and goes back to the start: back off, re-read, try again.
3. **While they go back, the row sits idle.** With pessimistic locking the lock passes straight to
   the next waiter, who already holds a fresh read. With optimistic locking, every hand-off costs a
   round trip of "fail → back off → re-read → re-queue".

The row's throughput falls from ~155/s to ~90/s, below the arrival rate. Once a system serves less
than arrives, latency doesn't just rise, **it grows without limit** until something gives: here,
k6 ran out of virtual users and dropped ~1,500 requests.

Optimistic locking isn't lock-free when the write itself takes a row lock. It just adds a failed
attempt to every hand-off.

## When is optimistic the right choice?

- **Low contention.** Profile edits, admin screens, rows that rarely collide. No locks are held while a
  human or a slow computation thinks.
- **Long "think" time between read and write.** For example, a user edits a form for 2 minutes. You
  can't hold a database lock for 2 minutes, but you can check a version when they press Save.
- **When you can't hold a connection.** A read in one request and a write in another (the form
  example again).

On a hot counter, use an atomic statement. If the check is too complex for one SQL statement, use
pessimistic locking.

## Try

- `make load ID=1.5 MODE=optimistic RETRIES=0`: give up on the first conflict. Latency drops to
  ~5 ms, and **32% of orders fail** with `too_many_conflicts` (we measured 1,450 of 4,501). Latency
  or errors: under contention, optimistic makes you choose.
- `make load ID=1.5 MODE=fixed RATE=250`: above the row's ceiling even the best strategy queues. We
  measured 158 orders/s served, average latency 2.6 s, 2,278 requests dropped. **Every hot row is a
  throughput ceiling.** Real systems split the counter: for example 10 "buckets" of stock per product,
  each its own row (FAILURE_TRACKER: hot partitions).

## Discussion

2. Where in your own projects is there a row that *everyone* updates (a counter, a balance, a
   "last updated" timestamp)?
3. The code already backs off randomly before retrying. Would a *longer* backoff help or hurt
   throughput here? Why?
