# 8.5 — Game day

> **Phase 8: operating it.** Everything so far had a runbook that told you what was broken. Real
> incidents don't. Practise finding the cause with only what on-call has: dashboards, alerts, traces, logs.

## Run it

```bash
make up PHASE=8
make load ID=8.5          # terminal 1: 15 minutes of normal traffic, healthy configuration
make gameday              # terminal 2, after a minute: one random fault, hidden
# ... investigate ...
make gameday-reveal       # what was it, and how long did you take?
make gameday-end          # undo it
```

`GAMEDAY_FAULT=<1-10> make gameday` picks a specific fault, for practising one you missed. Play in pairs: one person
runs `make gameday`, the other investigates without looking at the terminal.

## Rules

- Allowed: Grafana (dashboards, Explore → Loki, Explore → Tempo), Prometheus, Alertmanager, `curl
  localhost:8091/api/alerts`, Kafka UI, `make psql` for read-only queries.
- Not allowed: `make toggles`, `docker ps`, reading `.gameday`, `scripts/toxics.py`. On-call doesn't get a list of
  what someone changed. (That's a lesson in itself: in real incidents, the first question is "what changed?",
  and a deploy log or a feature-flag audit log answers it.)
- Write down, in this order: **impact** (who is affected, how badly), **where** (which service or dependency),
  **cause**, **evidence** (the panel, trace or log line that proves it), **mitigation** (what would you do right now?).

## A method that works

1. **Impact first.** Overview → error ratio and p99 per endpoint. Operating → checkout SLO, alerts firing. Which
   endpoints, which customers? All instances or one (*Requests per second by instance*, `X-Served-By`)?
2. **Follow the request.** Explore → Tempo: `{ duration > 1s }` or `{ status = error }`. Which span is slow or
   failing: our code, the database (`connection` / `query` spans), Redis, Kafka, the vendor?
3. **Check the resources behind that span.** USE method: Utilisation, Saturation, Errors. Postgres dashboard
   (connections, CPU, slow queries), Saturation dashboard (threads, pools), Kafka (lag per partition), Redis,
   Containers.
4. **Read the logs of the suspect.** Explore → Loki: `{container="core-2"} |= "ERROR"`, or click a trace's
   *Logs for this span*.
5. **Form a hypothesis, then look for the evidence that would disprove it.** "Postgres is slow" should show up as
   slow `query` spans on *every* instance, not just one.

## Postmortem

After `make gameday-reveal`, write a short blameless postmortem:

1. **Timeline**: when did the fault start, when did you notice, when did you know the cause?
2. **Detection**: which signal told you first? Did an alert fire, and was it the right one (a symptom, not a cause)?
3. **Diagnosis**: what slowed you down? A missing panel? A trace that broke at an async boundary (8.1)? A log line
   without a trace id?
4. **Action items**: one alert, one dashboard panel, one runbook line that would have made this faster.

The action items are the real output of a game day. Add the panel to `infra/grafana/gen_dashboards.py` or the alert
to `infra/prometheus/rules/alerts.yml`, and play again.
