# 6.5 — The same blast, through Kafka

> **Phase 6: notifications, from a sync call to Kafka.** Kafka as a shock absorber: the spike goes into
> a log, and consumers read it at their own pace.

## Run it

```bash
make load ID=6.5
```

`notification-mode=kafka-direct`: core publishes each notification to the `notifications` topic. Marketing blasts
**60,000 promos at 3,000/s**. notification-service (2 instances × 3 consumers) sends at the vendor's pace, about
300/s.

| | |
|---|---|
| Orders p95 / p99 during the blast | **10 ms / 11 ms** |
| Postgres CPU peak | 0.45 cores (orders and history only) |
| Peak consumer lag | **54,744 messages** |
| Backlog fully drained | **200 s after the run ended** |

Open **Kafka & notifications**: "Consumer lag" shoots up to ~55k, then slopes down steadily for over three minutes.
**Orders never notice.**

## How it works

```
 core ──produce──▶ [ topic "notifications": 6 partitions, an append-only log on disk ] ──consume──▶ notification-service
     3,000/s                    holds whatever hasn't been read yet                       ~300/s, at the vendor's pace
```

- **Producers don't wait for consumers.** Publishing means "the broker wrote it to its log" (`acks=all`), which
  takes milliseconds whether consumers are keeping up or not.
- **The log is the buffer.** Kafka stores messages on disk for a retention period (24 h here), whether or not
  anyone has read them. 55,000 messages is nothing; millions are routine.
- **Consumers pull.** Each consumer reads from its partitions as fast as *it* can process, and commits its position
  (offset) as it goes. Nobody pushes work at it faster than it can handle: that's **backpressure** by design.
- **Lag is the honest metric.** Lag = newest offset − committed offset = messages written but not yet processed.
  Growing then shrinking is healthy. Growing forever means you need more consumers (up to the partition count, K1)
  or a faster downstream.

## Measuring lag is harder than it looks

We tried three ways and two of them lied:

| Source | What it measured | Problem |
|---|---|---|
| kafka-exporter (`kafka_consumergroup_lag_sum`) | committed offsets | the series **vanishes** while a group rebalances; `missing` read as `0` told us "drained" when 55k were waiting |
| consumer metric (`records_lag`) | messages not yet **fetched** | consumers prefetch thousands into a local buffer: it reported 6,821 when the real backlog was 29,900 |
| **committed offsets via AdminClient** ([`LagReporter`](../../services/notification-service/src/main/java/dev/quickdrop/notification/LagReporter.java)) | messages not yet **processed** | — matches `kafka-consumer-groups.sh --describe` |

```bash
docker exec qd-kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group notification-service          # CURRENT-OFFSET, LOG-END-OFFSET, LAG per partition
```

Kafka UI (http://localhost:8085) shows topics, partitions, consumer groups and messages.

## What Kafka doesn't fix

- **The backlog still has to be worked off.** For 200 s, SMS were minutes late. Fine for promos, terrible for OTPs
  stuck behind them (6.8).
- **Publishing after commit is a dual write.** If core dies between the two, the event is lost (6.6).
- **At-least-once.** A consumer that crashes after sending but before committing will process the message again
  (K3).
