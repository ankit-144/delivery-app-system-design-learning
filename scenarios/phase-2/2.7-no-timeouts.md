# 2.7 — No timeouts

> **Phase 2: one box hits the wall.** The most common production mistake: waiting forever.

## Story

The SMS vendor's load balancer has a fault. It **accepts TCP connections and never answers**. There's no
error and no refusal. Our HTTP client's read timeout is `0`, which in Java means wait forever.

(2.1 had a *slow* vendor. This one is *silent*, which is worse: slow eventually answers.)

## Run it

```bash
make load ID=2.7 MODE=broken    # vendor-timeout-ms = 0
make load ID=2.7 MODE=fixed     # vendor-timeout-ms = 500
```

Toxiproxy's `timeout` toxic (with `timeout=0`) turns the vendor connection into a black hole. Then 20
orders/s, 20 browses/s and 2 health checks/s.

| | broken | fixed |
|---|---|---|
| Orders OK | **0%** | 100% (p50 506 ms) |
| Browse OK | 12% | 100% |
| Health checks OK | **8.5%** | 100% |
| Busy Tomcat threads | **49 / 50, stuck** | 13 |
| SMS | 0 sent during the run | 876 failed fast |

## Observe

- **Service saturation → Busy threads vs max**: climbs to 50 within ~2.5 s (20 orders/s, each thread
  stuck forever), then stays there. Nothing frees them.
- **Vendor call latency**: no data. The calls never complete, so they're never measured. **A hung
  call is invisible to latency metrics**; you only see it in thread counts and in-flight gauges.
- **JVM threads by state**: every request thread in `RUNNABLE`, blocked in a socket read.

Try it yourself: `make toxics` shows the black hole. During a broken run, take a thread dump (a
JVM prints one to its stdout when it receives `SIGQUIT`; the runtime image has no `jcmd`) and look
for request threads stuck in a socket read:

```bash
docker kill --signal=QUIT qd-core-1
docker logs --tail 3000 qd-core-1 2>&1 | grep -A 15 '"http-nio-8080-exec' | grep -m 5 -B 3 -A 8 'SocketInputStream\|NioSocketImpl'
```

## Why it's an outage, not a slowdown

With no timeout, the vendor's failure **becomes our failure** and doesn't stop. A slow dependency
(2.1) eventually answers and frees the thread. A silent one never does, so threads leak until there
are none. Customers can't even browse.

When the vendor came back (`teardown()` removes the toxic), **90 SMS that had been stuck the whole time
were finally sent**, minutes late, for orders whose customers had given up.

## Fix

Every network call needs a timeout. For each call, ask:

| Timeout | Our setting | Question it answers |
|---|---|---|
| Connect timeout | 2 s (`VendorClient`) | How long to wait for the TCP handshake? A dead host never completes it. |
| Read timeout | `vendor-timeout-ms` | How long to wait for bytes once connected? |
| Pool acquire timeout | `db-pool-timeout-ms` = 5 s | How long to wait for a free DB connection? |
| Overall deadline | (none yet) | How long can this *whole request* take, across all calls? |

With a 500 ms read timeout the black hole costs each order half a second and an SMS, and the app
stays up.

### Choosing a value

Start from the dependency's normal latency, not from a round number: our vendor answers in
~100 ms (p99 ~120 ms), so 500 ms gives headroom without letting a thread hang for long. Then check the
**budget**: if checkout must answer within 2 s, the vendor can't be allowed 5 of them.

## Timeouts alone are not enough

- **Every failed call still costs 500 ms of a thread.** At 200 orders/s that's 100 threads busy
  timing out. A **circuit breaker** notices the vendor is failing and stops calling it for a while,
  failing in microseconds instead (scenario 6.2).
- **Retries multiply load**: three retries with 500 ms timeouts = 2 s per order, and 4× the traffic to
  a struggling vendor (scenario 8.3).
- **Defaults are dangerous**: `HttpURLConnection` (0 = forever), JDBC (0 = forever), many Redis and
  Kafka clients (very long). **Assume every default timeout is wrong until you've checked it.**
