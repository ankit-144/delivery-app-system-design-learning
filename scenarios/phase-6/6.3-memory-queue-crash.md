# 6.3 — An in-memory queue, and the crash that empties it

> **Phase 6: notifications, from a sync call to Kafka.** "Make it async" is half an answer. Where does
> the queue live?

## Story

notification-service now answers core immediately (202 Accepted) and sends later. Core is fast again.
The vendor takes 500 ms and each instance has 4 sender threads: ~16 SMS/s go out while 30 orders/s come
in. A backlog builds. 30 s in, **notification-1 crashes** (an OOM kill, a bad deploy, a node failure)
and Docker restarts it.

## Run it

```bash
make load ID=6.3 MODE=broken    # delivery-mode=async-memory
make load ID=6.3 MODE=fixed     # delivery-mode=db-queue
```

After the run the script speeds the vendor up, waits for every backlog to drain, and **reconciles**
orders against the SMS the vendor actually received (`GET /admin/reconcile/sms`):

| | Orders | Order SMS received | **Orders that never got their SMS** |
|---|---|---|---|
| in-memory queue | 1,350 | 1,044 | **306** |
| Postgres queue | 1,351 | 1,298 | **53** |

## In-memory: lost without a trace

The backlog was a `LinkedBlockingQueue` in notification-1's heap
([`MemoryQueue`](../../services/notification-service/src/main/java/dev/quickdrop/notification/MemoryQueue.java)).
The crash took 306 messages with it. **No error, no log line, nothing on any dashboard.** core had received
202 for each of them. Only the reconciliation shows the gap.

The queue is also unbounded: a big enough blast fills the heap, the JVM dies of `OutOfMemoryError`
(`-XX:+ExitOnOutOfMemoryError`), and you lose everything at once. Try it:
`curl -X POST 'localhost:8091/admin/blast?count=2000000'` with `delivery-mode=async-memory`.

## Postgres queue: durable — almost

Each notification is a row in `notify.notifications` (its own schema on the shared Postgres). Worker threads
claim rows and send them ([`DbQueue`](../../services/notification-service/src/main/java/dev/quickdrop/notification/DbQueue.java)).
After the crash, the rows were still there and the workers carried on.

**Where did the 53 go?** Core counted exactly 55 `dropped` calls in that run. They were lost on the **HTTP hop**:
core picks a notification instance at random, and while notification-1 was down and restarting, calls to it
failed and core doesn't retry. A message is durable only *once it's stored*. Getting it there is the weak link.
6.6's outbox closes the gap by storing the message in the **same transaction as the order**, before any network
hop.

## Two bugs we hit building this (both classic)

1. **Claiming rows without a transaction.** The first version ran `SELECT … FOR UPDATE SKIP LOCKED` on its own.
   In autocommit mode the lock is released when the statement ends, so two workers could pick the same rows
   and send the same SMS twice. The fix is one atomic statement:

   ```sql
   UPDATE notifications SET status = 'SENDING', claimed_at = now()
   WHERE id IN (SELECT id FROM notifications WHERE status = 'PENDING' OR
                       (status = 'SENDING' AND claimed_at < now() - interval '30 seconds')
                ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED)
   RETURNING …
   ```

   The `claimed_at` lease means rows held by a worker that crashed are picked up again after 30 s.

2. **The wrong schema.** Flyway created the table in `notify`, but the app's connections searched `public`.
   Every insert failed, core counted them as `dropped`, and the first run of this scenario "lost" 1,197
   messages. The reconciliation caught a bug that every dashboard missed.

## Discussion

1. core got 202 Accepted for all 306 lost messages. What does "accepted" promise, and to whom?
2. Why is the 30 s lease needed? What happens without it when a worker crashes mid-send?
3. A Postgres queue is durable. Why isn't that the end of the story? (6.4)
