# 3.4 — Rider positions in each instance's memory

> **Phase 3: scale out.** Fast-changing shared state, the thing Redis is best at.

## Story

2,000 riders around the Indiranagar and Koramangala stores. Each phone pings its location about every
30 seconds; nginx spreads the pings over three instances. After 15 s of pings (the shift starting),
orders begin: 30 per second.

The first scaled-out version keeps "where is each free rider" in a map in each JVM
([`MemoryLocator`](../../services/core-service/src/main/java/dev/quickdrop/core/rider/strategy/MemoryLocator.java)).
It's fast, avoids 2.6's database load, and was right with one instance.

## Run it

```bash
make load ID=3.4 MODE=broken    # rider-locator=memory
make load ID=3.4 MODE=fixed     # rider-locator=redis-geo
make load ID=3.4 MODE=db        # db-nearby (2.6's fix), for comparison
```

| | memory | redis-geo | db-nearby |
|---|---|---|---|
| Assignment attempts that found **no rider** | **3,699 of 4,255** | 0 | 0 |
| Average distance to the assigned rider | 2.70 km | 2.06 km | 1.96 km |
| Free riders each instance knew at the end | **29 / 3 / 28** | — | — |

With riders standing free outside the store, 87% of matching attempts found nobody.

## Why

Each instance builds its picture from the events **it** handles:

- a ping lands on one instance, so the other two don't see it;
- an assignment happens on one instance, which removes the rider; the others still think they're free
  (the database check catches that);
- a delivery finishes on whichever instance's background job freed the rider, so only that instance
  adds them back.

Every instance has a partial, stale view, and gets worse over time as riders cycle through
busy → free on other instances. A deploy (restart) wipes the map completely.

## Fix: Redis GEO

[`RedisGeoLocator`](../../services/core-service/src/main/java/dev/quickdrop/core/rider/strategy/RedisGeoLocator.java)
keeps **available** riders in one GEO set per city, shared by every instance:

```bash
docker exec -it qd-redis redis-cli
GEOADD riders:available:1 77.6408 12.9784 4211          # a free rider pings (or finishes a delivery)
ZREM   riders:available:1 4211                          # the rider is assigned
GEOSEARCH riders:available:1 FROMLONLAT 77.6408 12.9784 BYRADIUS 5 km ASC COUNT 5 WITHDIST
TYPE   riders:available:1                               # "zset": a GEO set is a sorted set, scored by geohash
```

A geohash interleaves the bits of latitude and longitude into one 52-bit number, so nearby points get
nearby scores and "near me" becomes a range scan on a sorted set. Updating a position is an O(log N)
`ZADD`, which is cheap enough for every ping. (In Postgres, 2.6's design made every ping an `UPDATE`
on the hottest table.)

## A wrong turn worth knowing about

The first version of this locator put **every** rider in the GEO set and checked availability
afterwards. It failed almost as badly as the in-memory one (3,470 of 4,026 attempts found nobody).
The 60 riders nearest the store are exactly the ones who just got assigned, so the nearest 60 were
always busy. An index has to answer the actual question ("nearest **free** riders"), so the set now
holds only available riders.

That design creates a **dual write**: every status change goes to Postgres *and* to Redis. If a
Redis write fails, the two drift apart. The defences:

- Postgres stays the source of truth: candidates from Redis are re-checked before assignment
  (`RiderDao.keepAvailable`), and the conditional `UPDATE` from 1.2 has the final say.
- `POST /admin/riders/geo-sync` rebuilds the set from Postgres. Real systems run a reconciliation
  like this periodically.
- Phase 6 replaces "write to both" with *change events*: write once, let consumers update their indexes.

## Discussion

1. Why is a *map per instance* fine for a cache of product names but wrong for rider positions?
2. Riders who stop pinging (phone died) stay in the GEO set forever. How would you expire them?
   (Hint: a sorted set of "last seen" timestamps, or one key per rider with a TTL.)
3. Which is the source of truth for "where is rider 4211": Redis or Postgres? Does it matter?
