# 0.1 — A normal day: learn to read the dashboards

> **Phase 0: baseline.** One core instance, one Postgres, an SMS vendor. Before breaking anything,
> learn what *healthy* looks like. You can't spot abnormal if you've never seen normal.

## Run it

```bash
make up                 # if not already running
make load ID=0.1        # 5 minutes of normal traffic
```

~90 requests per second, mixed the way a real app's traffic is mixed:

| Stream | Rate | Endpoint |
|---|---|---|
| Browsing the catalogue | 40/s | `GET /api/stores/{id}/products` |
| Rider location pings | 30/s | `POST /api/riders/{id}/location` |
| Placing orders | 10/s | `POST /api/orders` |
| "My orders" | 5/s | `GET /api/customers/{id}/orders` |
| Login OTPs | 2/s | `POST /api/auth/otp` |

Most traffic is reads and pings. Orders, the thing that makes money, are about 10% of requests.
That's typical.

## The tour

Open http://localhost:3000. The home dashboard is **QuickDrop — Overview**. Hover the **(i)** on any
panel for what it shows and what to look for.

### 1. Is the product working? (Overview, top)

- **Invariant violations**: all green zeros. These are business rules checked by SQL every 5 s.
  They're the most important numbers on the screen, and most companies don't have them.
- **Orders per second by result**: ~10/s, almost all `placed`.
- **Order placement latency**: p50 around 120 ms. Why so slow for a few SQL statements? Because
  `notification-mode=inline` sends the SMS on the request thread and the vendor takes ~100 ms. Keep
  that in mind: it's the Phase 2 story.

### 2. RED: Rate, Errors, Duration (Overview, middle)

For every endpoint: how many requests, how many fail, how long they take. This is the **customer's
view**. If RED looks fine, customers are probably fine.

### 3. USE: Utilisation, Saturation, Errors (Service saturation)

For every **resource**: how busy is it, is work queueing for it, is it failing?

| Resource | Utilisation | Saturation (queueing) |
|---|---|---|
| Request threads | Tomcat busy threads (max 50) | open connections > busy threads |
| DB connections | Hikari active (max 10) | Hikari "waiting threads" |
| CPU | container CPU vs 1-core limit | CPU throttling |
| The vendor | vendor in-flight | async queue size |

At this load everything is far from its limit. **Write down the numbers**: busy threads ≈ 2–5, active
connections ≈ 1–2, CPU ≈ 0.1–0.2 cores. In Phase 2 you'll watch each of them hit the ceiling.

### 4. The database (Postgres)

- **Connections by state**: a handful `idle`, one or two `active`.
- **Top queries by total time**: which statements cost the most database time. The rider location
  `UPDATE` is probably near the top. It's tiny, but it runs 30 times a second.

### 5. Containers & logs

CPU and memory per container, and the logs of every container in one place (Loki). Filter with
`{service="core-1"}` or `{service="postgres"}`.

## Little's law: one formula for the whole course

> **concurrency = throughput × latency**

10 orders/s × 0.12 s each = **~1.2 orders in flight** at any moment. That's why one Tomcat thread and
one DB connection are enough for orders right now.

What happens if the vendor's latency goes from 0.1 s to 1 s? 10 × 1 = **10 threads busy** just waiting
for SMS. At 50 orders/s that's 50: every Tomcat thread we have. Hold that thought until scenario 2.1.

## Try

- `make load ID=0.1 MODE=fixed`: the correct strategies. At this traffic level the dashboards look
  *identical* to the naive ones. **Bugs from Phase 1 are invisible at normal load.** That's what
  makes them dangerous.
- `make load ID=0.1 SCALE=3`: three times the traffic. Which panel moves first?
- Keep `make load ID=0.1 MODE=keep DURATION=30m` running in a second terminal while you do other
  scenarios. Background traffic makes everything more realistic.
