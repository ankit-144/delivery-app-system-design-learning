# 6.6 — The dual write, and the transactional outbox

> **Phase 6: notifications, from a sync call to Kafka.** An order goes into Postgres; its event goes
> into Kafka. Two systems, and no transaction spans both.

## Run it

```bash
make load ID=6.6 MODE=broken    # kafka-direct: COMMIT, then publish. 5% "crash" in between
make load ID=6.6 MODE=in-tx     # kafka-in-tx: publish, then COMMIT. 5% roll back after publishing
make load ID=6.6 MODE=fixed     # outbox
```

20 orders/s for 30 s. Afterwards the script drains every backlog and reconciles orders with the SMS the vendor
received:

| Mode | Orders in Postgres | Order SMS at the vendor | Orders **without** an SMS | SMS for orders that **don't exist** |
|---|---|---|---|---|
| commit, then publish | 600 | 574 | **26** | 0 |
| publish, then commit | 575 | 601 | 0 | **26** |
| outbox | 601 | 601 | **0** | **0** |

## Why both orders are wrong

**Commit, then publish** ([`NotificationService.afterCommit`](../../services/core-service/src/main/java/dev/quickdrop/core/notification/NotificationService.java)):

```
 COMMIT order 1234      ✓ in Postgres
 ── process dies (deploy, OOM, node failure) ──
 publish event          ✗ never happens       → order exists, nobody is ever told
```

**Publish, then commit** (`insideTransaction`, `kafka-in-tx`):

```
 publish event          ✓ in Kafka, consumers already sending the SMS
 COMMIT order 1234      ✗ rolls back (stock check, constraint, timeout)   → an SMS for an order that doesn't exist
```

There's no order of the two calls that is safe, because there's no atomic "commit both". Distributed
transactions (2PC/XA between Postgres and Kafka) exist in theory and are almost never used: they're slow, and a
stuck coordinator blocks both systems.

## Fix: the transactional outbox

[`Outbox.java`](../../services/core-service/src/main/java/dev/quickdrop/core/notification/Outbox.java),
migration `V6__outbox.sql`:

```
 BEGIN
   INSERT INTO orders …
   INSERT INTO outbox (topic, key, payload) …        ← the event is just a row, in the SAME transaction
 COMMIT                                               ← both or neither

 relay, every 200 ms, on every core instance:
   BEGIN
     SELECT … FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED
     send each to Kafka, wait for acks
     UPDATE outbox SET published_at = now() WHERE id = ANY(…)
   COMMIT
```

- The order and its event **can't disagree**: they're one Postgres transaction.
- If Kafka is down, rows wait in the outbox and are published when it's back (**Kafka & notifications → Outbox
  relay**: "oldest unpublished").
- `SKIP LOCKED` lets the relay run on all three instances without publishing a row twice (3.6).
- If the relay crashes after Kafka acknowledged but before its `UPDATE` commits, those rows are published
  **again**. The outbox gives **at-least-once**, so consumers must be idempotent (K3).
- The outbox is a queue, not an archive: published rows are deleted after an hour.

In production the relay is often **Debezium** (change data capture): it reads the outbox table from the WAL and
publishes, with no polling.

## Reconciliation catches what dashboards don't

None of the 26 lost or 26 ghost messages produced an error a customer-facing dashboard would show. Only comparing
the two systems found them ([`ReconcileController`](../../services/core-service/src/main/java/dev/quickdrop/core/admin/ReconcileController.java)).
Payment companies, ledgers and marketplaces run jobs like this every night.

## Discussion

1. Why can't you fix the dual write by "retrying the publish"?
2. The outbox gives at-least-once delivery. Where do duplicates come from, and who must handle them?
3. Why does the relay use `SKIP LOCKED`? What would happen with three relays and plain `SELECT`?
