# 0.3 — Schema migrations with Flyway

> **Phase 0: baseline.** The schema is code. It's versioned, reviewed and applied automatically, and
> it's the one part of a deploy you can't simply roll back. Phase 4 changes the schema *under load*.
> This scenario is the vocabulary.

## How it works here

Migrations live in
[`services/core-service/src/main/resources/db/migration`](../../services/core-service/src/main/resources/db/migration):

```
V1__baseline_schema.sql    tables and indexes
V2__seed_data.sql          cities, stores, products, customers, riders
V3__rider_nearby_index.sql the index the rider locator needs (added in scenario 2.6)
...                        later phases add more
```

When core-service starts, Flyway:

1. takes a lock (so two instances starting together don't both migrate),
2. reads the `flyway_schema_history` table,
3. applies every `V<n>__*.sql` not yet applied, in version order, each in its own transaction,
4. records each one with a **checksum** of its contents.

Then Hibernate validates that the entity classes match the tables (`ddl-auto: validate`). The
application **never** creates or alters tables itself.

## Exercise 1: add a migration

Customers want to save a delivery note ("ring the bell twice").

We use version numbers in the 900s for exercises so they never collide with the project's own
migrations. Delete them and run `make clean` when you're done (see *Cleaning up*), otherwise
later phases' migrations would have *lower* numbers than one already applied, and Flyway refuses that.

1. Create `services/core-service/src/main/resources/db/migration/V900__customer_delivery_note.sql`:

   ```sql
   ALTER TABLE customers ADD COLUMN delivery_note TEXT;
   ```

2. Rebuild and restart: `make up` (rebuilds the image).
3. `make logs S=core-1` shows `Migrating schema "public" to version "900 - customer delivery note"`.
4. Check `flyway_schema_history` again, and `\d customers`.

Adding a nullable column with no default is instant even on a huge table: Postgres only updates
the catalog. Phase 4 shows which DDL is *not* instant.

## Exercise 2: edit a migration that already ran

1. Change `V900__customer_delivery_note.sql`, for example add `-- reviewed` at the end.
2. `make up`.
3. core-1 doesn't start. `make logs S=core-1`:

   ```
   Migration checksum mismatch for migration version 900
   -> Applied to database : 1234567890
   -> Resolved locally    : -987654321
   ```

The database ran the *old* file. Every other environment (your colleague's laptop, staging,
production) also ran the old file. If you could edit it, environments would silently diverge.
**Applied migrations are immutable. Fix forward with a new version.**

Undo the edit to get core-1 back up.

## Exercise 3: a migration that fails halfway

1. Create `V901__broken.sql`:

   ```sql
   ALTER TABLE customers ADD COLUMN loyalty_points INTEGER NOT NULL DEFAULT 0;   -- fine
   ALTER TABLE customers ADD COLUMN referral_code TEXT NOT NULL;                -- fails: 30,000 existing rows would be NULL
   ```

2. `make up`. Startup fails on the second statement: `column "referral_code" of relation "customers" contains null values`.
3. Check: `\d customers`. Is `loyalty_points` there?

   **No.** Postgres runs DDL inside transactions, so the whole migration rolled back. MySQL can't do
   this: its DDL auto-commits, and a failed migration there leaves a half-applied schema that needs
   manual repair.

Delete `V901__broken.sql` to get going again. (If Flyway recorded a failed row, `DELETE FROM
flyway_schema_history WHERE version = '901';`.)

## Cleaning up

Delete your `V9xx` files, then `make clean && make up`: the database is recreated from the project's own migrations (all data is deleted).

## What Phase 4 adds

Everything above assumed a quiet database and one instance. In production:

- **Migrations take locks.** Some `ALTER TABLE` statements block every read and write on the table
  while they wait and while they run (4.1).
- **Old code meets new schema.** During a rolling deploy, v1 instances run against the v2 schema
  (4.4).
- **Big data changes are slow.** Backfilling millions of rows in one transaction is its own outage
  (4.5).
