# 4.3 — Which `ALTER TABLE` rewrites the whole table?

> **Phase 4: changing the schema while the system is live.** Some DDL only touches the catalog.
> Some copies every row while nobody can read or write. They look almost identical.

## Run it

```bash
make load ID=4.3 MODE=fixed     # ADD COLUMN source TEXT NOT NULL DEFAULT 'app'
make load ID=4.3 MODE=broken    # ADD COLUMN public_ref UUID NOT NULL DEFAULT gen_random_uuid()
make load ID=4.3 MODE=widen     # ALTER TABLE order_items ALTER COLUMN quantity TYPE BIGINT
```

Traffic: 20 orders/s, 20 "my orders"/s.

| Change | Took | Orders p99 | Why |
|---|---|---|---|
| Add column, **constant** default | instant | 95 ms | Postgres stores the default once in the catalog; old rows "have" it without being touched (PG 11+) |
| Add column, **volatile** default (`gen_random_uuid()`) | **3.4 s** | **2.9 s** | each row needs its *own* value: every row is rewritten |
| Change type `INTEGER → BIGINT` | **1.6 s** | 1.1 s | the on-disk format changes: every row is rewritten (2.9M order items) |

During a rewrite Postgres holds **`ACCESS EXCLUSIVE`**: no reads, no writes, on 1.5 M rows here, which is
seconds on a laptop and **minutes to hours** in production.

## Rewrite or not: a cheat sheet

| Usually instant (catalog only) | Rewrites the table (or scans it under a heavy lock) |
|---|---|
| `ADD COLUMN` (nullable, or constant default) | `ADD COLUMN … DEFAULT <volatile expression>` |
| `DROP COLUMN` (just hidden; space reclaimed later) | `ALTER COLUMN … TYPE` (most type changes) |
| `RENAME COLUMN` / `RENAME TABLE` (but see 4.4!) | `SET NOT NULL` on an existing column: full scan to check, under `ACCESS EXCLUSIVE` |
| `ALTER COLUMN … SET DEFAULT` | `ADD PRIMARY KEY` / `UNIQUE` (builds an index without `CONCURRENTLY`) |
| `varchar(50) → varchar(100)` or `→ text` | `varchar(100) → varchar(50)` (has to check every row) |
| `ADD CONSTRAINT … NOT VALID` | `ADD CONSTRAINT CHECK/FK` without `NOT VALID` (scans everything) |

Even the instant ones need `ACCESS EXCLUSIVE` for a moment, so always use `lock_timeout` (4.1).

## Doing the expensive ones safely

**A unique per-row value** (like `public_ref`): add the column nullable → backfill in batches (4.5) →
set the default for new rows → enforce `NOT NULL` with a validated check constraint:

```sql
ALTER TABLE orders ADD COLUMN public_ref UUID;                                 -- instant
-- backfill in batches (4.5)
ALTER TABLE orders ALTER COLUMN public_ref SET DEFAULT gen_random_uuid();     -- only affects new rows
ALTER TABLE orders ADD CONSTRAINT public_ref_not_null CHECK (public_ref IS NOT NULL) NOT VALID;  -- instant
ALTER TABLE orders VALIDATE CONSTRAINT public_ref_not_null;                   -- scans, but allows reads and writes
ALTER TABLE orders ALTER COLUMN public_ref SET NOT NULL;                      -- PG 12+: uses the valid constraint, no scan
```

**A type change** (`INTEGER → BIGINT`, the classic "ids ran out at 2.1 billion"): add a new column,
dual-write, backfill, switch reads, drop the old one, which is the expand/contract of 4.4. Or plan
for `BIGINT` ids from day one, which is why QuickDrop's ids are `BIGINT`.
