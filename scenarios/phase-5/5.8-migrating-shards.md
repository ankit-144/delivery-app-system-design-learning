# 5.8 — A migration that fails on one shard

> **Phase 5: scaling the database.** Phase 4's migrations, times N databases, each with its own data.

Hands-on with curl. Phase 5 must be running.

## Story

The team adds a sanity constraint to sharded orders: totals must be positive
([`db/shard/V3__positive_totals.sql`](../../services/core-service/src/main/resources/db/shard/V3__positive_totals.sql)):

```sql
ALTER TABLE sharded_orders ADD CONSTRAINT sharded_orders_positive_total CHECK (total_paise > 0);
```

It passed on staging. But years ago an import script stored refunds as negative orders, and one of them
survived, on shard 1 only.

## Run it

```bash
curl -s localhost:8081/admin/sharding/status
# [{"shard":0,"schemaVersion":"2",...},{"shard":1,"schemaVersion":"2",...}]

curl -s -X POST 'localhost:8081/admin/sharding/legacy-row?shard=1'      # the old bad row
# {"shard":1,"totalPaise":-100,"note":"a refund imported as a negative order by an old script"}

curl -s -X POST 'localhost:8081/admin/sharding/migrate?target=3'
# [{"shard":0,"applied":1,"version":"3"},
#  {"shard":1,"error":"check constraint \"sharded_orders_positive_total\" ... is violated by some row"}]

curl -s localhost:8081/admin/sharding/status
# [{"shard":0,"schemaVersion":"3",...},{"shard":1,"schemaVersion":"2",...}]      ← schema drift
```

Now **the shards have different schemas.** Code written for V3 works on shard 0 and fails on shard 1, and
only for the customers or cities that live there. That's the worst kind of bug report: "it fails for
some users".

## Fix

```bash
docker exec qd-pg-shard-1 psql -U quickdrop quickdrop -c 'DELETE FROM sharded_orders WHERE total_paise <= 0'
curl -s -X POST 'localhost:8081/admin/sharding/migrate?target=3'
# [{"shard":0,"applied":0,"version":"3"},{"shard":1,"applied":1,"version":"3"}]
```

(In real life: fix the data properly, e.g. move refunds to a refunds table, in its own reviewed migration.)

## Lessons for N databases

- **Each shard is its own database with its own history.** Data that's impossible on one can exist on
  another. "Passed on staging" proves little.
- **Check before you constrain.** Add constraints `NOT VALID`, then `VALIDATE CONSTRAINT` per shard
  (4.3), and run a pre-flight query on every shard: `SELECT count(*) WHERE NOT (total_paise > 0)`.
- **Migrations must be idempotent and resumable per shard.** Flyway records the version per shard, so
  rerunning only applies what's missing (shard 0: `applied: 0`).
- **Track schema versions per shard on a dashboard**, and alert when they differ for longer than a deploy.
- **Code must tolerate both versions** during the rollout, exactly 4.4's expand/contract, now across shards.
- **Roll out gradually**: one canary shard first, then the rest.
