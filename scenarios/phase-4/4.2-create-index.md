# 4.2 — Building an index on a busy table

> **Phase 4: changing the schema while the system is live.** `CREATE INDEX` and `CREATE INDEX
> CONCURRENTLY` produce the same index with very different side effects.

## Story

Support wants to look orders up by a short public reference, an md5 of the order id. That needs an
expression index on 1.5 million orders:

```sql
CREATE INDEX orders_ref_lab_idx ON orders (md5(id::text));
```

On a laptop it builds in about 2 seconds. On a production table, think minutes. The shape of the
problem is the same.

## Run it

```bash
make load ID=4.2 MODE=broken        # CREATE INDEX
make load ID=4.2 MODE=fixed         # CREATE INDEX CONCURRENTLY
make load ID=4.2 MODE=interrupted   # CONCURRENTLY, cancelled halfway
```

Traffic: 30 orders/s (each one INSERTs into `orders`), 20 "my orders"/s (reads).

| | `CREATE INDEX` (2.2 s) | `CONCURRENTLY` (2.4 s) |
|---|---|---|
| Orders p99 / max | **1.8 s / 2.3 s** | 56 ms / 60 ms |
| "My orders" p99 | 777 ms | 51 ms |

## Why

| | Lock taken | Blocks reads? | Blocks writes? |
|---|---|---|---|
| `CREATE INDEX` | `SHARE` for the whole build | no | **yes, every INSERT/UPDATE/DELETE** |
| `CREATE INDEX CONCURRENTLY` | `SHARE UPDATE EXCLUSIVE` | no | no |

A plain build reads the table once and needs it frozen, so no writes for the duration: every order
INSERT waited the full 2.2 s. A concurrent build scans the table **twice**, waits for in-flight
transactions in between, and catches up with rows written meanwhile, so it's slower but lets writes
continue.

## The catch: interrupted concurrent builds

```bash
make load ID=4.2 MODE=interrupted
```

A long transaction is open (25 s). `CREATE INDEX CONCURRENTLY` has to wait for every transaction that
started before it, and our `lock_timeout = 5s` cancels it:

```
create-index-concurrently (lock_timeout 5000 ms) -> FAILED: canceling statement due to lock timeout
orders_ref_lab_idx: {"valid": false, "size": "48 MB"}
```

A failed concurrent build **leaves the index behind, marked INVALID**:

- the planner never uses it,
- but every INSERT and UPDATE still maintains it (paying the cost for nothing),
- and `CREATE INDEX CONCURRENTLY IF NOT EXISTS` sees it exists and does **nothing**, so a naive retry
  "succeeds" without fixing anything.

```sql
SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE NOT indisvalid;   -- find them
DROP INDEX CONCURRENTLY orders_ref_lab_idx;                                   -- then build again
```

Other rules for concurrent builds:
- It **can't run inside a transaction**. Flyway normally wraps each migration in one; on Postgres it
  recognises `CREATE INDEX CONCURRENTLY` and runs the migration outside a transaction, provided the file
  contains *only* non-transactional statements (so give it its own migration file). A script config
  file (`V7__index.sql.conf` with `executeInTransaction=false`) makes that explicit. QuickDrop's
  `SchemaController` runs it without `@Transactional` for the same reason.
- `DROP INDEX CONCURRENTLY` exists too. A plain `DROP INDEX` takes `ACCESS EXCLUSIVE` (4.1!).

## Discussion

1. Why can a plain `CREATE INDEX` allow reads but not writes?
2. Why does a concurrent build have to wait for transactions that started before it?
3. An INVALID index exists in production. What did it cost you, and how would you have noticed?
