# 3.8 — Cache stampede

> **Phase 3: scale out.** A cache that works 99.9% of the time and takes the database down for the
> other 0.1%.

## Story

Every app open shows "best sellers in your store". For store 1 that's 100 requests per second. The
query aggregates 90 days of orders, about **0.6 CPU-seconds of Postgres** per run, and Postgres has 2
CPUs. So it's cached in Redis for 10 seconds
([`BestsellerService`](../../services/core-service/src/main/java/dev/quickdrop/core/catalog/BestsellerService.java)).

```sql
EXPLAIN ANALYZE SELECT ... -- best sellers for store 1
-- Parallel Seq Scan on order_items ... Workers Launched: 2
-- Execution Time: 229 ms            (× 3 processes ≈ 0.6 CPU-seconds)
```

## Run it

```bash
make load ID=3.8 MODE=none      # no cache
make load ID=3.8 MODE=broken    # cache-aside, 10 s TTL
make load ID=3.8 MODE=fixed     # single-flight + stale copy
```

60 seconds at 100 requests/s. A perfect cache would run the query 6 times (once per 10 s).

| | no cache | cache-aside | single-flight |
|---|---|---|---|
| Expensive queries run | 5,837 | **1,411** | **6** |
| Postgres CPU peak | 2.01 / 2 | **2.02 / 2** | 0.12 |
| Requests OK | 1.5% | 78% | 100% |
| p99 | 8.7 s | 5.3 s | 1 ms |
| Served stale | — | — | 58 |

Cache-aside ran the query **235 times per expiry**.

## Why: the stampede

```
 t = 10.000 s   key expires
 t = 10.001 s   request 1: miss → start the 0.6 s query
 t = 10.011 s   request 2: miss → start another
 …              every request on every instance misses until someone writes the key back
 t = 10.6 s+    Postgres is running 60+ copies of the same query on 2 CPUs; each takes seconds, not 0.2 s
                → the window stays open longer → more misses → slower queries …
```

The stampede feeds itself: the more copies run, the slower each one gets, and the longer the key stays
empty. It repeats every 10 seconds. On **Postgres → container CPU** you can see it as a sawtooth.

## Fix: single-flight, with a stale copy

```
 miss → SET lock:bestsellers:1 NX PX 10000
          won:   run the query, write fresh (TTL 10 s) + stale copy (TTL 300 s), release
          lost:  return the stale copy now  (or wait ≤ 3 s for the fresh one, the first time ever)
```

Exactly one request per expiry pays for the query. Everyone else gets the previous list instantly. It's
at most 10 seconds old, and nobody notices for a best-sellers widget.

Related techniques you'll meet:

| Technique | Idea |
|---|---|
| **Single-flight / request coalescing** | one recompute per key; others wait or get stale (what we did) |
| **Stale-while-revalidate** | serve the stale value and refresh it in the background (HTTP has a header for it) |
| **Probabilistic early expiration** | each reader recomputes *slightly before* expiry with a small, growing probability, so one of them refreshes it before it's gone |
| **TTL jitter** | `TTL = 10 s ± random`, so thousands of keys written at the same moment (after a deploy or a cache flush) don't all expire together |
| **Refresh-ahead** | a background job recomputes hot keys on a schedule; requests never compute |

## The worst stampede: a cold cache

A Redis restart, `FLUSHALL`, or a deploy that changes cache key names empties *every* key at once.
The Redis deep-dive (R4) restarts Redis under load.
