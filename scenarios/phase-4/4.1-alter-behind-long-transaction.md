# 4.1 — An instant `ALTER TABLE` that freezes the table

> **Phase 4: changing the schema while the system is live.** The most common way a "harmless"
> migration causes an outage.

## Story

The product team wants coupon codes on orders. The migration is one line, and it's instant: adding a
nullable column only updates Postgres' catalog, not a single row.

```sql
ALTER TABLE orders ADD COLUMN coupon_code TEXT;
```

Meanwhile an analyst has a `psql` session open. They ran `SELECT … FROM orders` inside a transaction
five seconds ago and went to get coffee. Their session is *idle in transaction*.

## Run it

```bash
make load ID=4.1 MODE=broken
make load ID=4.1 MODE=fixed
```

Traffic: 20 orders/s, 20 "my orders"/s, 20 catalogue browses/s. Browsing never touches the `orders`
table, so it's the control group. At t=5 s the analyst's transaction starts (30 s); at t=10 s the
migration runs.

| | broken | fixed (`lock_timeout = 2s` + retry) |
|---|---|---|
| The ALTER took | **25 s** (waiting) | 28 s, done after 7 lock timeouts |
| Orders OK / p95 | 79% / **11.7 s** | 94% / 1.8 s |
| "My orders" OK / p95 | 81% / 11.1 s | 100% / 1.6 s |
| **Browse** (no `orders` table!) OK / p95 | **80% / 10.9 s** | 100% / 0.9 s |

## Why: the lock queue

Every query takes a lock on the tables it touches. A `SELECT` takes `ACCESS SHARE`, the weakest lock,
which conflicts only with `ACCESS EXCLUSIVE`. `ALTER TABLE` needs `ACCESS EXCLUSIVE`, if only for a
millisecond.

```
 t=5   analyst:    BEGIN; SELECT … FROM orders;    holds ACCESS SHARE (until COMMIT, 30 s later)
 t=10  migration:  ALTER TABLE orders …            wants ACCESS EXCLUSIVE → waits for the analyst
 t=10+ every new query on orders                   wants ACCESS SHARE / ROW EXCLUSIVE → waits behind the ALTER
```

Postgres grants locks **in order**. A new `SELECT` doesn't jump ahead of the waiting `ALTER`, even
though it doesn't conflict with the analyst. So one idle session plus one "instant" migration =
**every query on `orders` waits** until the analyst commits.

Watch **Postgres → Sessions waiting for a lock** fill up, and **Connections by state** show the
analyst as `idle in transaction`.

### Why browse suffered too

Browsing never touches `orders`. It failed anyway, because stuck order requests held Tomcat threads and
pool connections while they waited, and browse requests queued for those (2.1, 2.2 again). **A lock
problem on one table becomes an outage for the whole service** through shared resources.

## Fix

**1. Never wait for a lock in a migration.**

```sql
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN coupon_code TEXT;      -- fails fast instead of queueing
```

If the lock isn't available within 2 s, the ALTER gives up (`55P03`), the queue behind it drains, and
the migration retries a moment later. Each attempt blocks traffic for at most 2 s. In the fixed run it
failed 7 times while the analyst's transaction was open and succeeded the moment it closed.

With Flyway, put `SET lock_timeout` at the top of the migration file. Spring Boot's
`spring.flyway.init-sqls` can set it for all of them. Also add retries, for example in your deploy
pipeline.

**2. Kill forgotten sessions.**

```sql
ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';   -- terminate sessions idle in a transaction
ALTER SYSTEM SET statement_timeout = '30s';                     -- for app roles; not for migrations
```

**3. Find the blocker during an incident.**

```sql
SELECT pid, state, now() - xact_start AS tx_age, application_name, left(query, 60)
FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY xact_start;

SELECT pid, pg_blocking_pids(pid) AS blocked_by, left(query, 60)
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

`pg_terminate_backend(<pid>)` ends the blocker. (In our run: `application_name = 'analyst-psql'`.)

## Discussion

1. The ALTER only needed the lock for a millisecond. Why did queries wait 25 seconds?
2. Why doesn't Postgres let new `SELECT`s skip ahead of the waiting `ALTER`?
3. What's the danger of `lock_timeout` set too high? Too low?
