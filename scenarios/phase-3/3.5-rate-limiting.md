# 3.5 — Rate limiting a bot

> **Phase 3: scale out.** Four algorithms, one endpoint that costs money on every call.

## Story

`POST /api/auth/otp` sends an SMS with a login code, and every SMS costs us money. A bot discovers it
and starts requesting codes for the same phone number non-stop ("SMS pumping" fraud is a real and
expensive attack). The rule: **5 OTPs per phone number per minute.**

Two bots:
- **hammer**: 20 requests/s for one number, non-stop.
- **boundary**: has read how fixed windows work, and sends 5 requests in the last half-second of a
  minute and 5 more right after it ticks over.

## Run it

```bash
make load ID=3.5 MODE=off
make load ID=3.5 MODE=broken          # in-memory limiter in each instance
make load ID=3.5 MODE=redis-fixed     # shared counter per minute
make load ID=3.5 MODE=fixed           # sliding log in Redis
make load ID=3.5 MODE=token-bucket    # token bucket in Redis
```

Each run lasts 150 s to cover at least two minute boundaries. The verdict is the **most OTPs accepted
in any 60-second span**. The limit is 5.

| Limiter | hammer | boundary | Why |
|---|---|---|---|
| off | **1,178** | 15 | no limit |
| local (per instance) | **30** | 15 | 5 per instance × 3 instances, × 2 across a window edge |
| redis-fixed | **10** | **10** | correct per calendar minute, 2× across the boundary |
| redis-sliding | **5** | **5** | exact |
| redis-token-bucket | 9 | 5 | burst of 5, then 1 every 12 s: averages 5/min, by design |

## The algorithms

All four live in
[`Limiters.java`](../../services/core-service/src/main/java/dev/quickdrop/core/ratelimit/Limiters.java).
Each Redis one is a single Lua script, so check-and-update is atomic: two instances can't both read
"4" and both allow the 5th.

### Local (in-memory): broken by scale-out

A counter per phone per minute in each JVM. nginx spreads the bot's requests over three instances,
each allows 5, and the bot gets 15 per minute. (Same root cause as 3.1: state in one JVM is a third of
the truth.)

### Fixed window

```lua
local count = redis.call('INCR', 'rl:fixed:otp:+91…:' .. minute)   -- one key per calendar minute
if count == 1 then redis.call('PEXPIRE', key, 60000) end
return count                                                         -- allowed if ≤ 5
```

Cheap: one integer per key. But the windows are calendar minutes:

```
 12:00:59.5  ■■■■■  (5 allowed: window 12:00)
 12:01:00.1  ■■■■■  (5 allowed: new window 12:01)      → 10 in 0.6 seconds
```

### Sliding log

```lua
ZREMRANGEBYSCORE key 0 (now - 60000)    -- forget requests older than a minute
if ZCARD key < 5 then ZADD key now id   -- remember this one
```

Exact: never more than 5 in *any* 60 s. Costs one sorted-set entry per allowed request, which is fine
for 5/min and expensive for 10,000/min. (A *sliding window counter*, blending the current and previous
fixed windows, gets close to exact with two integers. Many API gateways use it.)

The script reads the time with `redis.call('TIME')`, **Redis' clock**, not each instance's. Three
app instances with slightly different clocks would otherwise disagree about which requests are older
than a minute.

### Token bucket

A bucket of 5 tokens refills at 5 per minute; each request takes one. Short bursts are allowed (an
honest user tapping "resend" twice), and the long-run average is enforced. The hammer got 9 in its
worst minute: the 5 saved-up tokens plus 4–5 refilled during that minute. That's not a bug, it's the
point of the algorithm. Choose it when you want to allow bursts, and the sliding log when you want a
hard ceiling.

## Where and how to rate limit

- **Key by what you're protecting.** OTP: per phone number *and* per IP *and* globally (a total SMS budget).
  Orders: per customer.
- **Answer 429 with `Retry-After`.** Good clients back off; bots don't, so watch the 429 rate per key.
- **Rate limits are a security control**, and the cheapest one there is. They also protect you from
  your own buggy clients retrying in a loop (8.3).
- **What if Redis is down?** Fail open or fail closed? See 3.9: we chose differently per endpoint.
