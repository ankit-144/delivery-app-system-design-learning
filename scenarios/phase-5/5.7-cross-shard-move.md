# 5.7 — Moving an order between shards

> **Phase 5: scaling the database.** With one database, "move this row" is one transaction. With two,
> it's two transactions, and anything can happen in between.

## Story

A customer switches their order from a Bengaluru store to a Mumbai store. With `shard-key=city`, the
order has to move from shard 0 to shard 1
([`ShardedOrderService.move`](../../services/core-service/src/main/java/dev/quickdrop/core/sharding/ShardedOrderService.java)):

```
INSERT the order on shard 1      (transaction on database 1)
DELETE the order from shard 0    (transaction on database 0)
```

`cross-shard-crash-percent=10`: one move in ten "crashes" in between, as if the instance died or the
network to shard 0 dropped.

## Run it

```bash
make load ID=5.7 MODE=broken    # a crash leaves the move half done
make load ID=5.7 MODE=fixed     # idempotent steps + the client retries
```

| | Moves completed | Crashed halfway | Completed by retry | Orders left on **both** shards |
|---|---|---|---|---|
| broken | 540 | 61 | 0 | **61** |
| fixed | 528 | 73 | 73 | **0** |

In the broken run, 61 orders exist twice. "My orders" shows them twice, the store screens of both cities
show them, and a rider might be dispatched from both stores.

## Why there's no simple fix

There's no transaction that spans two Postgres databases out of the box. The options:

| Approach | What it means |
|---|---|
| **Two-phase commit (XA, `PREPARE TRANSACTION`)** | both databases promise, then both commit. Correct, but slow, a coordinator crash leaves locks held, and many systems (and most teams) avoid it |
| **Idempotent steps + retry** (what `fixed` does) | `INSERT … ON CONFLICT DO NOTHING`, then `DELETE` by id. Retrying a half-done move just finishes it. Needs someone to *do* the retry: the client, a job, a queue |
| **Saga** | a sequence of local transactions, each with a compensating action (move failed? delete the copy, restore the original). The standard pattern across services |
| **Outbox + events** | record "move order 123" in the source shard's transaction; a relay performs the rest reliably (Phase 6, 6.6) |
| **Don't move rows** | choose a shard key that never changes for an order, e.g. the customer. Then this problem disappears |

What `fixed` relies on: **at-least-once execution + idempotent operations = exactly-once effect**. The
same principle carries through Phase 6 and 7 (Kafka consumers, K3).

## The id problem

Our Snowflake ids encode the shard an order was **created** on (5.4). After a move, the id points to
the wrong shard. `findById` asks the id's shard first and, on a miss, falls back to asking every shard
(`quickdrop_shard_lookup_misses_total`). Systems that move data either route through a **directory**
(key → current shard) or encode a logical bucket rather than a physical shard in the id (5.6).
