# 6.7 — The vendor allows 100 SMS per second

> **Phase 6: notifications, from a sync call to Kafka.** A queue doesn't make a downstream faster. It
> only lets you choose how to wait.

## Story

The SMS vendor's contract: **100 requests per second**, beyond that `429 Too Many Requests`. We have 2
notification instances × 3 consumers, each sending as fast as Kafka hands them messages. Marketing queues 20,000
promos.

## Run it

```bash
make load ID=6.7 MODE=broken    # no throttling
make load ID=6.7 MODE=local     # 90/s per instance
make load ID=6.7 MODE=fixed     # 90/s shared by all instances (Redis token bucket)
```

| Throttling | Accepted by the vendor | Rejected with 429 (**lost**) | Kafka lag after 60 s |
|---|---|---|---|
| none | 600 | **19,400** | 0 |
| 90/s **per instance** | 6,744 | **5,492** | 4,647 |
| 90/s **shared** (Redis) | 6,053 | **31** | 13,955 |

## What happened

**No throttling**: 6 consumers emptied the topic in seconds, the vendor accepted 100 per second and refused the
rest. 97% of the promos were lost: our notification-service doesn't retry 429s. "Lag 0" looks like success, and
it's the worst result.

**Per instance**: each instance allows 90/s, so 2 instances allow 180/s against a limit of 100: still 45% rejected.
It's 3.5 again: a limit enforced separately in each instance is multiplied by the instance count, and the vendor
doesn't care how many instances you have.

**Shared**: one token bucket in Redis for all instances
([`VendorRateLimiter`](../../services/notification-service/src/main/java/dev/quickdrop/notification/VendorRateLimiter.java),
the Lua script from 3.5). Consumers wait for a token before sending, so the vendor sees 90/s and almost
nothing is rejected (the 31 were the bucket's initial burst). The backlog waits **in Kafka**, where it's safe, as
lag.

That's the real point of a queue between you and a limited downstream: it converts **overload into lag**. Lag can
be waited out. A 429 you don't retry is a lost message.

## Other ways to handle a vendor limit

- **Retry 429s with backoff**, honouring `Retry-After`. But without a shared limiter, retries just add to the
  overload (8.3).
- **Priorities within the limit**: spend the vendor's 100/s on OTPs first (6.8).
- **More vendors**: route a share of traffic to a second SMS provider (a common real setup, also for redundancy).
- **Spread the blast**: marketing tools usually let you schedule a send over an hour.

## Discussion

2. What breaks if the shared limiter's Redis goes down? (Look at what `VendorRateLimiter` does then.)
3. You add a third notification instance. What happens in `local` mode? In `fixed`?
