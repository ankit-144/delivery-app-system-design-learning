# 5.5 — One city, one hot shard

> **Phase 5: scaling the database.** Sharding spreads data evenly only if the keys are spread evenly.

## Story

QuickDrop is a Bengaluru company: **80% of orders** come from Bengaluru, 10% each from Mumbai and Delhi.
With `shard-key=city` and two shards, cities map to shards by `(city - 1) % 2`: Bengaluru and Delhi on
shard 0, Mumbai on shard 1.

## Run it

```bash
make load ID=5.5 MODE=broken    # shard-key=city
make load ID=5.5 MODE=fixed     # shard-key=customer
```

400 orders/s for 45 s.

| | shard 0 | shard 1 |
|---|---|---|
| city key: writes/s | **306** | 34 |
| city key: rows | **16,162** | 1,839 |
| customer key: rows | 9,167 | 8,834 |

With the city key, shard 0 does **9×** the work of shard 1. On a laptop both cope. In production
the hot shard hits its CPU, IOPS and connection limits first, and **the system is only as big as its
hottest shard**. Adding shards doesn't help: Bengaluru is one key, so it can only be on one shard.

## What teams do

- **A finer key**: shard by *zone* or *store* instead of city. Bengaluru becomes 50 keys that can
  spread across shards, while an order's transaction stays local (store + its inventory).
- **Split the hot key**: give a hot tenant or city its own shard, or several (`bengaluru-1`,
  `bengaluru-2` by zone).
- **A directory instead of a formula**: a lookup table `key → shard` lets you place keys deliberately
  and move a hot one later (5.3, 5.6).
- **Hash the key**: the customer hash spreads perfectly, but gives up locality (5.2).

The same problem appears in every partitioned system: a hot partition in Kafka (one key with most of the
messages, K2), a hot key in Redis Cluster (R2), a hot partition in DynamoDB. The fix is always "a key
with more, smaller values".

## Watch it

**Redis & scale-out / Containers → CPU**: `pg-shard-0` vs `pg-shard-1`.
Prometheus: `sum by (shard) (rate(quickdrop_shard_queries_total[1m]))`.
