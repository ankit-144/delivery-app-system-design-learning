# 5.4 — Ids that collide across shards

> **Phase 5: scaling the database.** `BIGSERIAL` is a counter in one database. Two databases, two
> counters.

## Run it

```bash
make load ID=5.4 MODE=broken    # id-strategy=sequence: each shard's own sequence
make load ID=5.4 MODE=fixed     # Snowflake ids
```

Customers place an order, then open its page by id (`GET /api/sharded/orders/{id}`).

| | Order pages that showed exactly the right order | Pages that found several orders with that id |
|---|---|---|
| per-shard sequence | 454 | **447** |
| Snowflake | **900** | 0 |

```
ids present on more than one shard: {"idsOnMoreThanOneShard": 447, "examples": [1, 2, 3, 4, 5]}
```

Shard 0 and shard 1 both handed out 1, 2, 3… "Order 57" is two different orders. Worse, with the id
alone you can't even tell which shard to ask, so every lookup must ask **all** of them.

## Snowflake ids

[`SnowflakeIds`](../../services/core-service/src/main/java/dev/quickdrop/core/sharding/SnowflakeIds.java),
the layout Twitter popularised:

```
 0 | 41 bits: ms since 2025-01-01 | 5 bits: shard | 5 bits: instance | 12 bits: sequence
```

- **Unique without coordination**: each instance generates ids on its own; different instance bits
  mean no collisions.
- **Roughly time-ordered**: new ids are bigger, which keeps B-tree index inserts at the right edge (fast).
- **The shard is inside the id**: `(id >> 17) & 31`, so a lookup by id goes straight to one shard.
- **4,096 ids per millisecond per instance**: the generator waits for the next millisecond if it runs out.

Things that bite:

- **Clock going backwards** (NTP correction): ids could repeat. Ours refuses to go back in time and
  keeps counting from the last timestamp.
- **Instance ids must be unique.** Two instances with the same id bits can produce the same id. Ours
  takes the digits of `INSTANCE_NAME`; real systems lease ids from ZooKeeper, etcd, or the database.
- **JavaScript.** We hit this building the scenario: Snowflake ids are ~2^57, but JavaScript numbers are
  exact only up to 2^53. k6 parsed `234838981009739776` as a *different* number and every lookup missed.
  The API now sends ids as **JSON strings** (`"id": "234838981009739776"`), exactly why Twitter's API has
  `id_str`.

## Alternatives

| Scheme | Pros | Cons |
|---|---|---|
| UUIDv4 (random) | no coordination at all | 128 bits; random order hurts index locality; no shard inside |
| **UUIDv7** (time-ordered UUID) | standard, sortable, no coordination | 128 bits; no shard inside |
| Snowflake-style | 64 bits, sortable, shard inside | needs unique worker ids and a sane clock |
| Sequence with step (shard k: k, k+N, k+2N…) | simple | fixing N forever makes resharding awkward |
| Central id service (ticket server) | simple ids | a dependency on every insert |

## Discussion

1. Why does a time-ordered id make inserts faster than a random UUID?
2. What happens to Snowflake ids if a server's clock jumps one hour into the future, then back?
3. Our ids say which shard an order was *created* on. What happens when it moves (5.7)?
