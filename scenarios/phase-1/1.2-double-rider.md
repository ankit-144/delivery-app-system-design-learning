# 1.2 — Two orders get the same rider

> **Phase 1: correctness under concurrency.**

## Story

Lunch rush in Indiranagar. **200 riders** are online near the store and deliveries are quick, so
there's usually a free rider. But every order wants "the nearest free rider", and for orders
arriving at the same moment that's the *same* rider.

A rider should never carry two orders at once. Customers whose order was quietly given to a rider
who's already busy wait twice as long and then complain.

## Run it

```bash
make load ID=1.2 MODE=broken
```

200 riders, ~50 orders/s arriving at random moments, 30 s, `rider-assignment=naive`. Verdict:

```
FAIL rider_double_booked    violations=63
       {"rider_id":1158,"overlapping_pairs":2,"violations":1}
```

63 riders were assigned overlapping orders. With `RACE_WINDOW=2` it's ~120.

## Observe

**Overview → Correctness**: `rider_double_booked` goes red.
**Overview → Riders**: the pool hovers well above zero. This isn't a capacity problem; there
are free riders. It's purely a coordination problem.

```sql
-- riders currently holding more than one active order
SELECT rider_id, count(*), array_agg(id) AS orders
FROM orders WHERE status = 'RIDER_ASSIGNED'
GROUP BY rider_id HAVING count(*) > 1;
```

## Why

[`NaiveAssignment.java`](../../services/core-service/src/main/java/dev/quickdrop/core/rider/strategy/NaiveAssignment.java):

```java
if (riders.status(riderId) == AVAILABLE) {   // SELECT status FROM riders WHERE id = ?
    riders.markBusy(riderId, orderId);       // UPDATE riders SET status = 'BUSY', current_order_id = ? WHERE id = ?
}
```

It's the same check-then-act shape as 1.1. Order A and order B both read "AVAILABLE", both write
"BUSY". The second `UPDATE` waits for A's row lock, then goes ahead anyway, because nothing in its
`WHERE` clause says "only if still available".

The locator makes it worse: every order at the same store ranks riders the same way, so they all
go for candidate #1 together.

> **A wrong turn we took building this scenario.** The first version had only 20 riders and sent
> orders evenly spaced. It found no bug. With 20 riders they were all busy almost all the time, and
> the background job assigned freed riders one at a time. Evenly spaced requests never overlapped.
> Real traffic is random and riders are usually available, which is when the race bites. **A load
> test that doesn't look like production can prove a broken system correct.**
> See [arrival patterns](1.1-oversell.md#about-arrival-patterns-and-the-race-window).

## Fix

```bash
make load ID=1.2 MODE=fixed
```

[`ConditionalAssignment.java`](../../services/core-service/src/main/java/dev/quickdrop/core/rider/strategy/ConditionalAssignment.java):

```sql
UPDATE riders SET status = 'BUSY', current_order_id = ?
WHERE id = ? AND status = 'AVAILABLE'
```

One row updated means we got the rider. Zero means someone else did, so try the next candidate. The
losing transaction waits for the winner's row lock, re-reads the row, sees `BUSY`, and updates
nothing.

Watch **Overview → Rider assignment → lost races (conditional)**. Every lost race there was a
double booking with the naive strategy.

## Defence in depth: let the database say no

Application logic can have bugs. A constraint can't be skipped. Try adding one by hand:

```sql
-- At most one active order per rider. (Run it after a fixed run, or it fails on existing duplicates.)
CREATE UNIQUE INDEX one_active_order_per_rider ON orders (rider_id) WHERE status = 'RIDER_ASSIGNED';
```

Now run `MODE=broken` again: the naive strategy's duplicates fail with a unique violation
(500 `internal_error`) instead of silently corrupting data. A loud failure beats a quiet one.

```sql
DROP INDEX one_active_order_per_rider;   -- put it back the way it was
```

## What can still go wrong

- **The background job and requests race each other.** With several instances, the
  `PendingRiderJob` runs on all of them (scenario 3.6).
- **The rider's phone disagrees with the database.** The rider went offline a second ago, but the
  database still says AVAILABLE. Distributed state is never perfectly fresh → FAILURE_TRACKER.
- **Fairness.** The nearest rider always wins and far riders starve. That's a product problem
  that matters at scale.
