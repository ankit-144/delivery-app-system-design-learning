# 5.6 — Resharding: how much data has to move?

> **Phase 5: scaling the database.** Mostly arithmetic, and it decides how painful growth will be.

## The question

You have 2 shards and add a third. Each key must end up on its new owner. **What share of all keys has
to move?** The ideal answer is 1/3: the new shard takes its fair share, and nothing else moves.

```bash
curl -s 'localhost:8081/admin/sharding/resharding?from=2&to=3'
curl -s 'localhost:8081/admin/sharding/resharding?from=8&to=9'
```

What the calculator
([`ShardingAdminController.resharding`](../../services/core-service/src/main/java/dev/quickdrop/core/sharding/ShardingAdminController.java))
measured over 100,000 keys:

| Growth | Ideal | `hash % N` | Consistent hashing (100 virtual nodes) | 256 logical buckets |
|---|---|---|---|---|
| 2 → 3 | 33.3% | **66.5%** | 36.1% | 33.2% |
| 3 → 4 | 25.0% | **74.8%** | 27.2% | 25.0% |
| 4 → 5 | 20.0% | **80.0%** | 18.0% | 19.9% |
| 8 → 9 | 11.1% | **88.8%** | 12.6% | 10.9% |

## Modulo: the trap

`shard = hash(key) % N`. Change N and almost every key's remainder changes: going from 8 to 9 shards
moves **89%** of the data, to add 11% more capacity. And while it's moving, every key's location is in
question.

## Consistent hashing

Shards own arcs of a ring of hash values; a key belongs to the first shard clockwise from its hash. A
new shard takes over parts of a few arcs, and only those keys move. Each shard gets 100 *virtual nodes*
(positions) so the arcs even out. With 2 shards and few virtual nodes, one shard can own far more of
the ring than the other.

**A wrong turn worth knowing:** our first version placed virtual nodes with a weak hash (one multiply).
Evenly spaced inputs came out evenly spaced, the arcs were badly lopsided, and the new shard got only
14.6% instead of ~33%. A good hash (MurmurHash3's two-round finalizer) fixed it. Consistent hashing is
only as good as its hash function.

Used by Cassandra, DynamoDB, Riak, memcached clients, and many load balancers.

## Logical buckets (pre-splitting)

Fix a large number of **logical** shards up front, say 256 buckets: `bucket = hash(key) % 256`. Then a
small table maps buckets → physical databases. Adding a database means reassigning some **whole buckets**
to it: exactly the ideal share moves, and you move a bucket as a unit (copy it, switch the mapping,
delete the old copy).

Used by Redis Cluster (16,384 hash slots), Vitess (keyspace ranges), Citus (shard counts), Kafka (a topic's
partition count, chosen once, K1). The bucket count is the one number you can't change easily, so choose
far more than you need.

## Moving data without downtime (the hard part)

The arithmetic says *how much*; operations decide *how*:

1. Copy the bucket's rows to the new shard (snapshot + catch up on changes, e.g. logical replication).
2. Briefly stop writes to that bucket (or dual-write), let the copy catch up.
3. Flip the directory entry: bucket → new shard.
4. Delete the old copy once nothing reads it.

Vitess, Citus and Spanner automate this. Doing it by hand is a project.
