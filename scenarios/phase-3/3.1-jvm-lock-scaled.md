# 3.1 — The JVM lock, on three instances

> **Phase 3: scale out.** core-1 is CPU-bound and the code is reasonable, so we add instances behind
> the load balancer. A new class of bug appears: **anything kept in one JVM's memory is now only a
> third of the truth.**

## Setup

```bash
make up PHASE=3      # adds core-2, core-3, Redis, exporters; nginx switches to round-robin
```

Check it: `for i in 1 2 3 4 5 6; do curl -s -o /dev/null -w "%header{x-served-by} " localhost:8080/api/products/1; done`
prints `core-2 core-3 core-1 core-2 core-3 core-1`.

> Right after `make up` you might see only `core-1` for a while. nginx marked core-2 and core-3 as
> failed while they were still booting (`max_fails=3`) and waits `fail_timeout=10s` before trying
> them again. That's lesson zero of load balancing: **an instance that's starting isn't an instance
> that's ready.**

## Story

1.1's flash sale again: 200 units, ~100 customers per second. In Phase 1 we fixed it with
`inventory-reservation=synchronized`, a JVM lock held around the transaction, and it was correct.

## Run it

```bash
make load ID=3.1 MODE=broken       # synchronized
```
```
FAIL oversold_units         violations=161
instances: 3
```

The fix from Phase 1 is broken. Nobody changed a line of code.

## Why

```
             nginx (round-robin)
           /        |         \
     core-1       core-2       core-3
  lock(store 1)  lock(store 1)  lock(store 1)     ← three different objects in three JVMs
       \            |            /
          Postgres: one inventory row
```

`synchronized` only excludes threads **in the same JVM**. core-1's lock knows nothing about core-2's.
Two requests on different instances run the naive read-check-write at the same time: the lost update
from 1.1 is back.

The same trap shows up everywhere state lives in memory: caches (3.3), maps of positions (3.4), rate
limit counters (3.5), "only run this once" flags (3.6).

## Fix

```bash
make load ID=3.1 MODE=redis-lock   # same idea, lock moved to Redis: correct (0 oversold)
make load ID=3.1 MODE=fixed        # atomic UPDATE: correct, and never needed a lock outside Postgres
```

Two very different fixes:

1. **Share the lock**: put it where every instance can see it. Redis `SET key token NX PX ttl` is the
   classic approach. It works, but distributed locks fail in ways JVM locks don't. Scenario 3.2 breaks it.
2. **Don't lock at all**: let the database do the read-modify-write atomically (1.1's `atomic`). The
   row lock lives in Postgres, which every instance already shares.

**Prefer the second.** A distributed lock adds a network hop to every order, a new single point of
failure (3.9), and subtle expiry bugs (3.2). Reach for one only when the protected work isn't a
single database operation, for example coordinating a call to an external system.
