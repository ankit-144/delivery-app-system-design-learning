# 2.4 — A missing index

> **Phase 2: one box hits the wall.** The cause behind 2.3, found the right way: from the
> database's own statistics.

## Story

The "My orders" screen worked fine at launch, when the table had a few thousand rows. A year later
there are 1.4 million orders, and the screen times out. So does checkout.

## Run it

```bash
make load ID=2.4 MODE=broken    # drops the index (if present)
make load ID=2.4 MODE=fixed     # CREATE INDEX CONCURRENTLY ... (customer_id, created_at DESC)
```

The first run seeds a year of history (~1.4M orders, ~15 s). Then 40 history requests/s, 10 orders/s
and 2 health checks/s for 60 s.

| | broken | fixed |
|---|---|---|
| "My orders" p50 | **20.5 s** | 2 ms |
| Orders p50 (a different endpoint!) | **24.4 s** | 3 ms |
| Health checks OK | 22% | 100% |
| Postgres CPU | **2.01 of 2** | 0.84 peak (includes building the index) |

## Find it like you would in production

Pretend you don't know the answer. You see slow requests; where do you look?

**1. Is it the app or the database?** *Service saturation*: Hikari `active` = max, many `waiting
threads`. *Containers*: **postgres CPU at 2.0**, core-1 nearly idle. The database is working flat out.

**2. Working on what?** *Postgres → Top queries by total time*. One statement dominates:

```
select o1_0.id from orders o1_0 where o1_0.customer_id=$1 order by o1_0.created_at desc fetch first $2 rows only
```

**3. Why is that query expensive?** *Postgres → Rows read by sequential scans, per table*: `orders`
at **tens of millions of rows per second**. Each request reads the whole table to find ~50 rows.

**4. Confirm with the plan.**

```bash
make psql
```
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM orders WHERE customer_id = 4242 ORDER BY created_at DESC LIMIT 20;
```
```
 Limit  (actual time=19.2..20.9 rows=20)
   ->  Gather Merge  (Workers Launched: 2)
         ->  Sort  (Sort Key: created_at DESC)
               ->  Parallel Seq Scan on orders  (rows=22 loops=3)
                     Filter: (customer_id = 4242)
                     Rows Removed by Filter: 499978          ← read 1.5M rows to keep 66
 Execution Time: 20.9 ms
```

20 ms looks harmless, until you notice it used **3 processes**. That's ~60 ms of CPU per request, so 2
CPUs can serve ~30 of these per second, and we send 40. The queue grows without limit, and every
other query waits behind it.

## Fix

```sql
CREATE INDEX CONCURRENTLY orders_customer_created_idx ON orders (customer_id, created_at DESC);
```

(`MODE=fixed` runs it for you through an admin endpoint, `SchemaController.java`.)

```
 Limit  (actual time=0.026..0.088 rows=20)
   ->  Index Scan using orders_customer_created_idx on orders  (rows=20)
         Index Cond: (customer_id = 4242)
 Execution Time: 0.105 ms
```

Two hundred times faster, on one process instead of three. And because the index is sorted by `created_at DESC` within each customer,
Postgres reads the first 20 entries and stops: no sort.

**Why `CONCURRENTLY`?** A plain `CREATE INDEX` blocks every write to the table until it finishes. On
a busy `orders` table that means checkout stops for the whole build. `CONCURRENTLY` takes longer but
lets writes continue. Phase 4 (4.2) shows the difference under load, including what happens when a
concurrent build fails halfway.

## Why didn't anyone notice at launch?

With 5,000 orders, a full scan takes 0.1 ms, which no dashboard would ever flag. **Missing indexes are
time bombs**: the cost grows with the data, not the traffic. Ways to catch them before they go off:

- Load-test against **production-sized data** (that's why this scenario seeds 1.4M rows).
- Watch `seq_tup_read` per table and the top of `pg_stat_statements` *as trends*, not only during incidents.
- Run `EXPLAIN` on new queries in code review.

## Indexes aren't free

Every index slows down every `INSERT` and `UPDATE` (the index must be updated too), uses disk and
memory, and must be vacuumed. `orders` already has 6. Don't index everything; index what your queries
filter and sort on.
