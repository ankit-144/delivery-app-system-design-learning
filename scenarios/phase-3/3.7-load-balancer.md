# 3.7 — What the load balancer does when an instance is slow or dies

> **Phase 3: scale out.** More instances means more chances for one of them to be sick.

## The setup

nginx sits in front of core-1..3 ([`infra/nginx`](../../infra/nginx)):

```nginx
upstream core {
    server core-1:8080 max_fails=3 fail_timeout=10s;   # 3 failures within 10 s → skip it for 10 s
    server core-2:8080 max_fails=3 fail_timeout=10s;
    server core-3:8080 max_fails=3 fail_timeout=10s;
    keepalive 64;                                      # reuse connections to the instances
}
proxy_next_upstream error timeout;                     # retry on another instance if the request never got an answer…
                                                       # …but never for POST/PATCH once it was sent (non-idempotent)
```

The traffic: 40 orders/s + 80 browses/s.

## Part 1: one slow instance

```bash
make load ID=3.7 MODE=slow     # core-2 gets +300 ms on every request (request-delay-ms toggle)
```

| | round-robin | least-conn (`make lb ALGO=least-conn`) |
|---|---|---|
| p50 | 7 ms | 6 ms |
| p95 | **308 ms** | **306 ms** |
| core-2's share of requests | 33% | **~10%** (752 vs ~3,200 each for the others) |

**Round-robin** sends each instance every third request, however busy it is. A third of customers get
core-2's 300 ms.

**Least connections** sends each request to the instance with the fewest open requests. A slow
instance holds connections longer, so it gets fewer new ones automatically. That cut core-2's share
from 33% to 10%, but p95 didn't move, because 10% of traffic still lands there and p95 sits right on
it. Least-conn mitigates a slow instance; it doesn't remove it.

What removes it:
- **Outlier detection** (Envoy, service meshes): eject an instance whose latency or error rate is far
  worse than its peers.
- **Active health checks** that measure something real: a dependency check or a latency threshold, not
  just "the process answers".
- **Hedged requests**: for idempotent reads, send a second copy elsewhere if the first hasn't answered
  by the p95.

Put nginx back afterwards: `make lb ALGO=round-robin`.

## Part 2: an instance dies

```bash
make load ID=3.7 MODE=crash      # 15 s in, core-3 calls Runtime.halt(): like kill -9 or an OOM kill
make load ID=3.7 MODE=graceful   # 15 s in, core-3 shuts down properly: like a deploy
```

Docker's restart policy brings core-3 back ~20 s later (watch **Redis & scale-out → Requests per second
by core instance**: core-3's line drops to zero and returns).

| | crash | graceful |
|---|---|---|
| Failed requests | **5** | **1** |
| p99 | 156 ms | 145 ms |
| max | ~1 s | ~1 s |

**Crash.** Requests in flight on core-3 die with the process. nginx retries what it safely can: GETs,
and requests that never reached the instance (connection refused). It does **not** retry a POST that
was already sent, because it can't know whether the order was created. Those 5 customers got a 502.
(Their retry is safe only because of 1.3's idempotency keys.)

**Graceful.** `server.shutdown=graceful`: Tomcat stops accepting new connections, finishes the
requests it has, then exits. Almost nothing is lost, but not *nothing*. The one failure is the classic
**keep-alive race**: nginx sends a request on an idle keep-alive connection at the moment core-3
closes it, so the request gets no answer, and it's a POST, so it isn't retried.

How production deploys close that gap:

1. Take the instance **out of the load balancer first** (fail its readiness probe, deregister it).
2. Wait for in-flight requests and for the LB to notice (a few seconds).
3. Then shut down gracefully.

Kubernetes does 1 and 3 for you, and the "wait" in between is usually a `preStop` sleep that people
forget.

## Part 3: startup

Watch the first seconds after `make up PHASE=3`: nginx can send requests to an instance that's
running but still booting Spring, and marks it failed. **Started is not ready.** That's what readiness
probes (`/actuator/health/readiness`) are for, and why nginx OSS (no active health checks) only learns
from failed requests.
