# 8.3 — A retry storm

> **Phase 8: operating it.** Retries turn a brief hiccup into an outage that outlives its cause.
> The trigger lasts 10 seconds; the outage lasts until the traffic stops.

## Story

OTPs go core → notification-service → SMS vendor, synchronously. The vendor works through requests with 20 workers
at 50 ms each, about 400 sends/s, and 2% of sends fail at random all the time. Login traffic is a steady 150 OTPs/s.
At t=15 s the vendor has a 10-second hiccup: 250 ms per send, ~80/s. At t=25 s it's fine again.

## Run it

```bash
make up PHASE=8          # Phase 6+ works too, without traces
make load ID=8.3 MODE=none      # no retries anywhere
make load ID=8.3 MODE=broken    # 3 immediate retries at core AND at notification-service
make load ID=8.3 MODE=fixed     # 2 retries at notification-service only: exponential backoff + jitter, 10% budget
```

The script prints a timeline from Prometheus (10 s steps). Abridged:

| | steady state (t=10 s) | after the trigger is gone (t=40–70 s) | duplicate OTPs at the vendor | OTP latency p50 / p99 |
|---|---|---|---|---|
| no retries | 147 ok/s, 3 lost/s (the 2%) | **recovered** by t=40: 147 ok/s | 0 | 54 ms / 504 ms |
| immediate retries, 2 layers | 150 ok/s, 0 lost (retries hide the 2%) | **0 ok/s, 102–143 lost/s, until the load stops** | **16,985** | **8,009 ms** / 10,462 ms |
| backoff + jitter + budget, 1 layer | 150 ok/s, 0 lost | **recovered** by t=40: 150 ok/s | 63 | 53 ms / 503 ms |

In the broken run, after the trigger: the vendor processed 420–515 sends/s, 350–430/s of them duplicates;
notification-service took **6.4 s** per request on average; retries ran at ~400/s at core and ~900/s at
notification-service; k6 couldn't even start 981 of its requests (no free virtual user). Switching the trigger off
took the script 6 attempts (see below), and the run printed so: the hiccup really was over.

## What happened in the broken run

The vendor was back to normal at t=25 s. The system never was. For the rest of the run the vendor was busier than
ever (420–515 sends/s), yet core counted **zero** successful SMS, because all of that work was
**retries of requests whose callers had already given up**:

```
 core ──2 s timeout──▶ notification-service ──500 ms timeout──▶ vendor
   └ 3 retries            └ 3 retries
 one OTP = up to 4 × 4 = 16 vendor attempts
```

1. The hiccup makes vendor calls slower than notification-service's 500 ms timeout. Each timeout is retried at once:
   4× the vendor traffic.
2. notification-service now takes longer than core's 2 s timeout, so core retries too, starting *new*
   notification requests while the old ones are still retrying. The vendor sees up to 16× the load.
3. The vendor keeps working on requests nobody is waiting for. Every one it completes is a real SMS: 16,985 times a
   customer got an OTP they'd already received.
4. When the hiccup ends, the load the vendor sees is still far above 400/s, because it's made of retries. Slow
   responses cause timeouts, which cause retries, which keep responses slow. This is a **metastable failure**:
   the trigger is gone, the overload sustains itself. Only removing load ends it (here, the end of the test; in
   production, often a full restart of the callers or blocking traffic at the edge).

## The fix, in three parts

[`Retrier`](../../libs/quickdrop-common/src/main/java/dev/quickdrop/common/resilience/Retrier.java):

1. **Retry at one layer.** Retries multiply across layers (4 × 4 = 16). Pick the layer closest to the failure
   (notification-service → vendor) and make every layer above it fail fast (core: no retries, circuit breaker).
2. **Back off, with jitter.** Wait `random(0, 100 ms × 2^attempt)` (capped at 2 s) before retrying. Exponential
   gives the downstream time to recover. *Full jitter* spreads retries out so thousands of callers don't come back
   in the same millisecond.
3. **A retry budget.** Every call earns 0.1 token, every retry spends 1. Retries can add at most ~10% to the load,
   however bad things get. When the downstream is overloaded, retries stop instead of multiplying the overload.
   (gRPC, Envoy and Finagle all ship this idea.)

And the fixed run gets the upside of retries too: the 2% random vendor failures are retried away (0 lost at steady
state), something the no-retry run can't do.

## Observe

- **Operating → Retry amplification**: retries per call. Broken: ~3 at each layer. Fixed: under 0.1.
- **Kafka & notifications → Vendor: accepted vs rejected**, with *duplicates*.
- Tempo: `{ name = "http post /api/auth/otp" && duration > 5s }`. A broken-run trace shows core's four 2-second
  attempts back to back.

## Two things we hit while building this

- **The retry storm ran notification-service out of memory.** With virtual threads, Tomcat's thread limit no longer
  bounds concurrency: every connection gets a thread. Thousands of in-flight retried requests exhausted the heap and
  the instance died, making things worse. notification-service now caps `server.tomcat.max-connections` at 1,000:
  bounded concurrency is a memory limit too.
- **We couldn't switch the trigger off.** The script's call to restore the vendor's latency timed out (it now retries,
  and needed 6 attempts): the admin API shares the vendor's HTTP port, and that port was drowning. Production services put management endpoints on a
  separate port (`management.server.port`) for exactly this reason.

## Related

- Timeouts must shrink as you go deeper: here core waits 2 s for notification-service, which waits 0.5 s × 4
  attempts (+ connection time) for the vendor. When the inner budget exceeds the outer one, the caller gives up
  while the callee keeps working.
- Idempotency keys (1.3, K3) don't reduce the load of a retry storm, but they stop it from texting customers twice.
- A queue (Phase 6) gives you natural backpressure: Kafka consumers can't be "retried at" by their producers.
