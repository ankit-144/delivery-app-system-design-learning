# 1.4 — Deadlocks on multi-item carts

> **Phase 1: correctness under concurrency.** We fixed 1.1 with row locks. Row locks have their
> own failure mode.

## Story

Breakfast time. Everyone's cart has milk and bread. Some customers add milk first, some add
bread first. The app sends the items in the order they were added.

## Run it

```bash
make load ID=1.4 MODE=broken
```

`inventory-reservation=pessimistic`, `inventory-lock-order=as-given`, ~30 carts/s, half
`[milk, bread]` and half `[bread, milk]`. `per-line-delay-ms=10` stands in for per-item work done
while the row is locked (pricing, promotions, checking a substitute).

What we measured:

```
pg deadlocks last 40s: 65
http_req_duration: med=23ms  p(95)=8.97s  max=20.6s
checks_succeeded: 91.73%      ← 8% of orders failed
```

## Observe

**QuickDrop — Postgres**
- **Deadlocks**: dozens per minute.
- **Sessions waiting for a lock**: a constant queue of `ShareLock` waiters.
- **Active connections by wait type**: `Lock` dominates; the database is mostly *waiting*, not working.

**QuickDrop — Overview**
- **API errors by type**: `deadlock`, and soon `db_pool_exhausted`.
- **Order placement latency**: p50 looks fine, p99 is many seconds.

**QuickDrop — Service saturation**
- **Connections: active / idle / waiting**: the pool is pinned at 10 with threads waiting. Every
  transaction stuck on a lock holds a connection, so the deadlock spreads to requests that have
  nothing to do with milk or bread.

The Postgres log shows each one (`make logs S=postgres`):

```
ERROR:  deadlock detected
DETAIL:  Process 812 waits for ShareLock on transaction 90211; blocked by process 815.
         Process 815 waits for ShareLock on transaction 90209; blocked by process 812.
```

## Why

```
 cart A = [milk, bread]                       cart B = [bread, milk]
 lock milk  ✓
                                              lock bread ✓
 lock bread … waits for B
                                              lock milk  … waits for A
                     ── neither can ever proceed ──
```

Postgres checks for cycles only after a lock wait reaches `deadlock_timeout` (1 s here). Then it
kills one transaction (`40P01 deadlock detected`). So each deadlock costs **a second of everyone
waiting plus a failed order**. In that second, other carts queue behind the stuck ones, take more
connections, and the pool runs dry.

> Plain `UPDATE`s deadlock too. They take row locks just like `SELECT … FOR UPDATE`:
> `make load ID=1.4 MODE=broken-atomic`.

## Fix

```bash
make load ID=1.4 MODE=fixed
```
```
pg deadlocks last 40s: 0
http_req_duration: med=23ms  p(95)=23.6ms  max=27.7ms
checks_succeeded: 100.00%
```

[`LineOrdering.java`](../../services/core-service/src/main/java/dev/quickdrop/core/order/LineOrdering.java)
sorts the cart by product id before locking. If every transaction takes locks in the same global
order, a cycle is impossible: whoever holds milk can always get bread eventually.

## Other tools, and when to use them

| Tool | What it does |
|---|---|
| Consistent lock order | Prevents deadlocks. The real fix. |
| `lock_timeout = '2s'` | Gives up waiting instead of queueing forever. Fails fast, doesn't prevent anything. |
| Retry on `40P01` | Deadlocks are transient: retrying the whole transaction usually succeeds. Do this *as well as* fixing the order. |
| Shorter transactions | Less time holding locks → fewer chances to collide. (Our `per-line-delay-ms` is the opposite.) |
| `NOWAIT` / `SKIP LOCKED` | Don't wait at all. Great for job queues (Phase 6), wrong for stock. |

## What can still go wrong

- **Locks you didn't know about.** Foreign keys take `KEY SHARE` locks on the referenced row, and
  triggers update other tables. Ordering your own statements doesn't cover those.
- **Across services.** Two services locking resources in each other's databases can deadlock in
  ways no single database can detect. That's distributed deadlock → FAILURE_TRACKER.

## Discussion

1. Why did requests that only ordered *eggs* also get slow during the broken run?
2. Postgres picked one transaction to kill. Should our API retry it automatically before answering
   the customer?
3. Why is `deadlock_timeout` 1 s and not 1 ms? What would checking more often cost?
