# 1.1 — Overselling the last units

> **Phase 1: correctness under concurrency.** One instance, one database. Nothing is slow.
> The data is just wrong.

## Story

Diwali flash sale. Store 1 (Indiranagar) has **200 units** of product 42 at a silly price.
The push notification goes out and 100 customers per second tap "Buy".

200 orders should succeed. Everyone else should see "out of stock".

## Run it

```bash
make load ID=1.1 MODE=broken
```

The script sets `inventory-reservation=naive`, sets stock to 200, and sends ~100 orders/s for 30 s,
arriving at random moments like real customers. At the end it prints the verdict:

```
FAIL oversold_units         violations=27
       {"store_id":1,"product_id":42,"total_stocked":200,"quantity":0,"sold":227,"violations":27}
FAIL stock_mismatch         violations=1
```

**227 units sold out of 200.** 27 customers paid for something that doesn't exist. Numbers vary a
little between runs (we see 25–30); they're never 0. Make it dramatic with `RACE_WINDOW=5` (~120 oversold).

## Observe

**Grafana → QuickDrop — Overview**

- **Correctness → Invariant violations**: `oversold_units` turns red within seconds.
- **Orders per second by result**: `placed` keeps going well after the stock should have run out,
  then everything turns into `OutOfStockException`.

Now check what the shelf says:

```bash
make psql
```
```sql
SELECT quantity, total_stocked FROM inventory WHERE store_id = 1 AND product_id = 42;
-- quantity = 0, total_stocked = 200. The shelf looks perfectly fine.

SELECT count(*) FROM orders o JOIN order_items i ON i.order_id = o.id
WHERE o.store_id = 1 AND i.product_id = 42 AND o.created_at >= (SELECT started_at FROM scenario_marker);
-- 227
```

The stock never went negative. A `CHECK (quantity >= 0)` constraint would not have caught it.
The bug is invisible unless you reconcile orders against stock, which is exactly what the
invariant checker (`InvariantChecker.java`) does every 5 seconds.

## Why

[`NaiveReservation.java`](../../services/core-service/src/main/java/dev/quickdrop/core/inventory/strategy/NaiveReservation.java):

```java
int available = inventory.quantity(storeId, productId);   // SELECT quantity ...
if (available < line.quantity()) throw new OutOfStockException(...);
inventory.setQuantity(storeId, productId, available - 1); // UPDATE ... SET quantity = <what we computed>
```

Two requests interleave:

```
 request A                          request B
 SELECT quantity  → 10
                                    SELECT quantity  → 10
 10 >= 1, ok                        10 >= 1, ok
 UPDATE quantity = 9
 COMMIT
                                    UPDATE quantity = 9      ← overwrites A's write
                                    COMMIT
```

Two units sold, the shelf went down by one. This is a **lost update**. Postgres' default isolation level
(READ COMMITTED) does nothing to stop it: each statement sees committed data, and nothing ties the
`SELECT` to the later `UPDATE`.

### About arrival patterns and the race window

The race needs two requests inside the same ~1 ms gap. Two things decide how often that happens:

- **How requests arrive.** Real customers act independently, so arrivals are random and clumpy (a
  *Poisson process*). Some land within a millisecond of each other even at 100/s. The script models
  this. If you send requests perfectly evenly spaced, 10 ms apart, they almost never overlap, and
  the bug hides. That's one reason load tests with evenly paced traffic miss race conditions.
- **How wide the gap is.** `RACE_WINDOW=5` makes the naive strategy pause 5 ms between read and
  write. Production has narrow gaps but enormous traffic, and GC pauses, slow queries at peak and
  network hops stretch them. The knob lets laptop traffic recreate that.

A cold JVM (right after `make restart S=core-1`) is slower, so requests overlap more and it races
more. **"Works on my machine, breaks at peak"** is exactly how these bugs ship.

## Fix — a ladder of options

Run each one and compare the graphs. Every mode resets stock to 200.

| Mode | Strategy | Result | What it costs |
|---|---|---|---|
| `sync-in-tx` | `synchronized` block inside the transaction | **still oversells**, just less (try `RACE_WINDOW=5`) | Looks fixed in code review. It isn't. |
| `synchronized` | JVM lock held around the whole transaction | correct | Serialises every order of the store, and **only works with one instance** (scenario 3.1) |
| `pessimistic` | `SELECT … FOR UPDATE` | correct | Buyers queue on the row lock, each holding a DB connection |
| `optimistic` | `version` column, write only if unchanged, retry | correct | Wasted retries when the item is hot (scenario 1.5) |
| `fixed` | `UPDATE … SET quantity = quantity - 1 WHERE quantity >= 1` | correct | Nothing worth mentioning: usually the right answer for a counter |

```bash
make load ID=1.1 MODE=sync-in-tx
make load ID=1.1 MODE=synchronized
make load ID=1.1 MODE=pessimistic
make load ID=1.1 MODE=optimistic
make load ID=1.1 MODE=fixed
```

### Why `synchronized` inside the transaction fails

[`SynchronizedInTxReservation.java`](../../services/core-service/src/main/java/dev/quickdrop/core/inventory/strategy/SynchronizedInTxReservation.java)
releases the lock when `reserve()` returns, but the transaction commits later, after the rider is
assigned and the order inserted. The next thread gets the lock, reads the **old committed** value
(our write isn't visible yet), and the lost update is back. The classic version of this bug is a
`synchronized` method annotated with `@Transactional`: the proxy commits *after* the method (and its
lock) has returned.

[`SynchronizedReservation.java`](../../services/core-service/src/main/java/dev/quickdrop/core/inventory/strategy/SynchronizedReservation.java)
gets it right by overriding `aroundTransaction` so the lock covers the commit (see
[`OrderService.java`](../../services/core-service/src/main/java/dev/quickdrop/core/order/OrderService.java)).

### Why the atomic UPDATE works

```sql
UPDATE inventory SET quantity = quantity - 1 WHERE store_id = 1 AND product_id = 42 AND quantity >= 1
```

Check and write are one statement. When two run at once, the second waits for the first's row lock,
then **re-evaluates the WHERE clause against the new row version**. If the stock is gone, it updates
0 rows and we answer "out of stock". There's no gap to race in.

## Verify

```bash
make load ID=1.1 MODE=fixed
```
```
OK   oversold_units         violations=0
OK   stock_mismatch         violations=0
```

## What can still go wrong

- **Two instances.** `synchronized` breaks the moment there's a second JVM. That's scenario 3.1.
- **Stock in a cache.** If product pages show stock from Redis, the page and the database disagree
  (scenario 3.3). Customers see "in stock", tap buy, get "out of stock". Annoying, but not a correctness bug.
- **Multi-item carts.** Locking several rows in different orders deadlocks (scenario 1.4).
- **Stock across shards or services.** Once inventory and orders live in different databases, there's
  no single transaction anymore → see *Sagas* in [FAILURE_TRACKER](../../docs/FAILURE_TRACKER.md).

## Discussion

1. The naive strategy never made stock negative. What other "the numbers look fine" bugs could hide in
   a system without an invariant checker?
2. Why does `pessimistic` hold a DB connection while waiting, and what happens when 50 requests
   wait on the same row with a pool of 10 connections?
3. `fixed` answers "out of stock" by updating 0 rows. How would you tell a customer *how many* are
   left if they asked for 3 and only 2 remain?
4. When would you pick `optimistic` over `fixed`? (Hint: what if the "check" is more complex than
   `quantity >= n`?)
