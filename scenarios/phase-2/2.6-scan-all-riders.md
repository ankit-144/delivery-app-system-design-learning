# 2.6 — Rider matching that loads every rider

> **Phase 2: one box hits the wall.** This time it's the application's CPU.

## Story

The first matching algorithm, written when Bengaluru had 50 riders: load every rider in the city,
keep the available ones, compute the distance to the store, sort, take the nearest ten. Clear and
easy to test. Now the city has **20,000 riders**, and it still runs on every single order.

## Run it

```bash
make load ID=2.6 MODE=broken    # rider-locator = db-scan
make load ID=2.6 MODE=fixed     # rider-locator = db-nearby
```

150 orders/s plus 20 browses/s and 2 health checks/s. The fixture grows Bengaluru's fleet to
20,000 riders (once; they stay).

| | broken (db-scan) | fixed (db-nearby) |
|---|---|---|
| Orders served | collapsing | **150 / s** |
| Order p50 | **36 s** | 4 ms |
| Health checks OK | **3%** | 100% |
| core-1 CPU | **1.0 of 1** (100% throttled) | ~0.75 at peak |
| Requests dropped by k6 | 5,422 | 0 |

## Observe

**Service saturation → Container CPU (cores) vs limit**: core-1 flat at its 1-CPU limit.
**CPU throttling**: 100%. In every 100 ms period the container wanted more CPU than its quota, and
the kernel paused it.

**Notice the gaps in the graphs.** Several core-1 panels go blank during the broken run. Prometheus
scrapes `/actuator/prometheus` every 5 s, and a CPU-starved JVM can't answer in time, so the scrape
fails and there's no data. **Your monitoring goes dark exactly when you need it most.** Two habits
help: alert on missing data (`up == 0`, `absent(...)`), and give the metrics endpoint its own thread
or port so it isn't stuck behind request traffic.

Compare this signature with 2.1:

| | 2.1 (threads) | 2.6 (CPU) |
|---|---|---|
| Busy threads | 50 / 50 | 50 / 50 |
| CPU | **low** | **at the limit** |
| What threads are doing | waiting on a socket | computing |

Both show "threads maxed, latency high". **CPU tells you which problem you have.**

## Why

[`DbScanLocator.java`](../../services/core-service/src/main/java/dev/quickdrop/core/rider/strategy/DbScanLocator.java):

```java
riders.findByCityId(cityId)          // 20,000 rows → 20,000 JPA entities
      .filter(AVAILABLE)             // in Java
      .map(haversine distance)       // in Java
      .sorted().limit(10)            // in Java
```

For each order: transfer 20,000 rows, build 20,000 objects (each tracked by Hibernate's persistence
context for dirty checking), compute 20,000 distances, sort, then throw 19,990 away. At 150 orders/s that's
**3 million entities per second** on one CPU.

## Fix

[`DbNearbyLocator`](../../services/core-service/src/main/java/dev/quickdrop/core/rider/strategy/DbNearbyLocator.java)
asks the database for exactly what it needs:

```sql
SELECT id, lat, lon FROM riders
WHERE city_id = ? AND status = 'AVAILABLE'
  AND lat BETWEEN ? AND ? AND lon BETWEEN ? AND ?     -- a ~5 km box around the store
ORDER BY (lat - ?)^2 + ((lon - ?) * cos(radians(?)))^2
LIMIT 10
```

backed by an index that only contains available riders
([`V3__rider_nearby_index.sql`](../../services/core-service/src/main/resources/db/migration/V3__rider_nearby_index.sql)):

```sql
CREATE INDEX riders_available_nearby_idx ON riders (city_id, lat) WHERE status = 'AVAILABLE';
```

Ten rows come back instead of 20,000. **Filter where the data lives.**

## It's not over

- The bounding box is a crude approximation (it uses the latitude index, then filters longitude). Real
  systems use geospatial indexes: PostGIS with a GiST index, H3 or geohash cells, or **Redis GEO**
  (scenario 3.4), which keeps rider positions in memory where updating them is cheap.
- Rider locations change every few seconds. Updating 20,000 rows every 5 s is 4,000 writes per
  second on the hottest table in the database, which is another reason locations move to Redis in Phase 3.
