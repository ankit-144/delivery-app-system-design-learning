# 5.2 — Choosing a shard key: every choice has a losing query

> **Phase 5: scaling the database.** Replicas multiply reads. When *writes* or data size outgrow one
> machine, you split the data: **sharding**.

## The sharding lab

Sharding the whole order flow would mean rewriting most of QuickDrop, so Phase 5 uses a focused lab
([`services/core-service/.../sharding`](../../services/core-service/src/main/java/dev/quickdrop/core/sharding)):
a `sharded_orders` table that exists on **two separate Postgres databases**, `pg-shard-0` and
`pg-shard-1`, with an app-side router that decides which shard owns each order. The code is small
enough to read in one sitting; 5.3 walks through it.

```bash
curl -s -X POST localhost:8080/api/sharded/orders -H 'Content-Type: application/json' \
     -d '{"customerId": 3, "storeId": 1, "totalPaise": 25000}'
# {"id":"234838981009739776","shard":0,...}
curl -s localhost:8081/admin/sharding/status
```

## Story

Customers order mostly in their home city; 10% order in another city (travel, family). Two screens
matter:

- **"My orders"**: all orders of one customer.
- **Store screen**: today's orders of one dark store.

Shard 1 sits on slower hardware today: +50 ms per query (Toxiproxy).

## Run it

```bash
make load ID=5.2 MODE=city        # shard-key=city
make load ID=5.2 MODE=customer    # shard-key=customer
```

| Shard key | "My orders": shards asked, p50 | Store screen: shards asked, p50 |
|---|---|---|
| **city** | **2 (every shard), 52 ms** | 1, 3 ms |
| **customer** | 1, 1 ms | **2 (every shard), 52 ms** |

## Why

**Shard by city**: an order lives on its store's shard. The store screen asks one shard. But a customer's
orders can be in any city, so "My orders" must **scatter-gather**: ask every shard in parallel, merge,
sort, return. It's as slow as the **slowest** shard, every time (p50 = 52 ms, shard 1's delay).

**Shard by customer** (hash of the customer id): "My orders" is one shard, but a store's orders are
spread over every shard, so the store screen pays the scatter.

There's no free choice. Pick the key that matches the **most frequent and most important** query, and make
the other one cheaper:

- **A second copy indexed the other way**: e.g. a per-store table on the store's shard, or a search
  index, kept in sync by events (Phase 6).
- **Accept the scatter** for rare queries (admin screens, analytics).
- **Precompute** the expensive cross-shard views.

## A good shard key

| Property | Why | Our keys |
|---|---|---|
| High cardinality | many values to spread over many shards | customer ✓, city ✗ (only 3) |
| Even load | no single value dominates | customer ✓, city ✗ (Bengaluru, 5.5) |
| Present in most queries | so queries can be routed to one shard | city: store queries; customer: "My orders" |
| Immutable | moving rows between shards is painful (5.7) | customer ✓; a store's city never changes ✓; an *order's* store can |
| Keeps transactions on one shard | cross-shard transactions don't exist (5.7) | city keeps order + store + local stock together ✓ |

Quick-commerce companies typically shard by **geography** (city or zone): an order, its dark store's
inventory and its riders all live together, so placing an order is a single-shard transaction. They pay
for "My orders" with a separate customer-keyed read model.
