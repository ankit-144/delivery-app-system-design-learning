# 2.5 — N+1 queries

> **Phase 2: one box hits the wall.** Every query is fast. There are just far too many of them.

## Story

The index from 2.4 is in place and "my orders" is fast again. But the database team asks why this
endpoint runs **3,000 statements per second** for 60 requests per second.

## Run it

```bash
make load ID=2.5 MODE=broken    # lazy loading
make load ID=2.5 MODE=fixed     # two queries
```

60 history requests/s. Toxiproxy adds **1 ms** to every Postgres response, roughly a database in
another availability zone of the same cloud region.

| | broken (lazy) | fixed (two-step) |
|---|---|---|
| SQL statements per request (avg) | **54.5** | 2 |
| SQL statements per second (Postgres) | **3,236** | 186 |
| "My orders" p50 with 1 ms DB latency | **66 ms** | 4 ms |
| "My orders" p50 with 0 ms (`DB_LATENCY=0`) | 2 ms | 1 ms |
| CPU (core / Postgres) | ~4× higher | baseline |

## Observe

- **Service saturation → JPA statements per request (p95)**: ~96 for the history endpoint.
- **Postgres → Top queries by calls**: two tiny statements called thousands of times per second:

  ```
  select i1_0.order_id,i1_0.id,i1_0.price_paise,i1_0.product_id,i1_0.quantity from order_items i1_0 where i1_0.order_id=$1
  select p1_0.id,p1_0.category,p1_0.name,p1_0.price_paise,p1_0.sku from products p1_0 where p1_0.id=$1
  ```

- Run `make load ID=2.5 MODE=broken DB_LATENCY=0`: on the same machine, Postgres answers in
  microseconds and the problem nearly disappears from the latency graph. **N+1 hides on your laptop**
  and shows up in the cloud, where every round trip costs a millisecond.

## Why

[`OrderHistoryService`](../../services/core-service/src/main/java/dev/quickdrop/core/order/OrderHistoryService.java)
in naive mode:

```java
orders.findByCustomerIdOrderByCreatedAtDesc(customerId, Limit.of(20))   // 1 query: 20 orders
      .stream().map(OrderView::of)                                       // for each order:
                                                                         //   order.getItems()        → 1 query
                                                                         //   item.getProduct().name  → 1 query per new product
```

`items` and `product` are **lazy** associations: JPA loads them the first time you touch them, one
query at a time. 1 + 20 + ~35 ≈ **55 round trips** for one screen. The "N" in N+1 is the number of rows
in your page, and nothing in the code looks like a loop over the database.

## Fix

```java
List<Long> ids = orders.findIdsByCustomer(customerId, Limit.of(20));     // 1 query: the page of ids
orders.findWithItems(ids);                                                // 1 query: join fetch items + products
```

```sql
select distinct o from Order o left join fetch o.items i left join fetch i.product where o.id in :ids
```

Why two queries rather than one fetch join with `LIMIT 20`? Joining items multiplies the rows (an order
with 3 items appears 3 times), so SQL `LIMIT 20` would cut orders in half. Hibernate knows this, and
when you combine `join fetch` with pagination it **loads every order of the customer into memory** and
paginates in Java, with a warning (`HHH90003004`) nobody reads. Page by ids first, then fetch the
graph for exactly those ids.

Other fixes you'll meet:

| Technique | Trade-off |
|---|---|
| `@BatchSize` / `hibernate.default_batch_fetch_size` | Lazy loads go in batches (`WHERE id IN (…)`): 55 queries become ~3 with a one-line config. Good default. |
| `@EntityGraph` | Declares what to fetch per repository method. |
| DTO projection (`select new OrderRow(...)`) | Fetch exactly the columns the screen needs; no entities at all. Fastest, but more code. |
| `FetchType.EAGER` | **Don't.** It fixes this screen and makes every other query that touches `Order` load items it doesn't need. |

## How to catch it

- Count statements per request in tests or in metrics (we use a Hibernate `StatementInspector`,
  `SqlStatementCounter.java`).
- Watch **calls**, not just **time**, in `pg_stat_statements`. N+1 never shows up as a slow query.
