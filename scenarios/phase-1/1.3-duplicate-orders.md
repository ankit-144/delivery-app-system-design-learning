# 1.3 — The customer taps "Pay" twice

> **Phase 1: correctness under concurrency.**

## Story

The customer's network is flaky. They tap "Place order", the spinner spins, they tap again. Or
the app's HTTP client times out after 5 s and **retries automatically**, while the first request
is still being processed on the server.

Either way, the server receives the same order twice. The customer expects one order and one charge.

## Run it

```bash
make load ID=1.3 MODE=broken
```

Each iteration sends the **same request twice at the same moment**, with the same
`Idempotency-Key` header, as a well-behaved client would. 20 pairs per second for 30 s:

```
FAIL duplicate_orders       violations=600
✗ both taps returned the same order
```

Every single pair became two orders: 600 customers charged twice, 600 extra riders dispatched.

## Observe

- **Overview → Invariant violations**: `duplicate_orders`.
- The client sent a key, and the server stored it in `orders.client_request_id`, but nothing
  enforced it:

```sql
SELECT customer_id, client_request_id, count(*), array_agg(id)
FROM orders
WHERE client_request_id IS NOT NULL AND created_at >= (SELECT started_at FROM scenario_marker)
GROUP BY 1, 2 HAVING count(*) > 1
LIMIT 5;
```

## Why

Two identical requests are two independent transactions. Neither knows the other exists. "Check if
we already have this order" in Java doesn't help: both checks run before either insert commits,
which is the same check-then-act race as 1.1.

## Fix

```bash
make load ID=1.3 MODE=fixed
```
```
OK   duplicate_orders       violations=0
✓ both taps returned the same order
```

[`IdempotencyDao.java`](../../services/core-service/src/main/java/dev/quickdrop/core/order/IdempotencyDao.java)
and the first step of
[`OrderService`](../../services/core-service/src/main/java/dev/quickdrop/core/order/OrderService.java):

```sql
INSERT INTO idempotency_keys (customer_id, idempotency_key) VALUES (?, ?) ON CONFLICT DO NOTHING
```

This runs **first, inside the order transaction**:

```
 tap 1                                     tap 2
 BEGIN                                     BEGIN
 INSERT key  → 1 row (claimed)
                                           INSERT key  → waits: tap 1 holds that key, uncommitted
 reserve stock, insert order...
 COMMIT                                    → 0 rows: key exists → load tap 1's order → return it (HTTP 200)
```

The primary key on `(customer_id, idempotency_key)` makes the database the referee. If tap 1 had
failed (out of stock) and rolled back, tap 2's insert would succeed and it would try again. A
retry after a failure gets a fresh attempt.

The replay answers **HTTP 200 with `Idempotent-Replay: true`** instead of 201, so clients and
dashboards can tell the two apart (**Overview → Orders per second → replayed**).

## What can still go wrong

- **The client must send a key.** No key, no protection. The key must be generated **once per
  intent** (when the user opens checkout), not per HTTP attempt.
- **Different payload, same key.** A real implementation stores a hash of the request and rejects a
  reused key with a different body (HTTP 422). Ours doesn't.
- **Keys forever?** The table grows without limit. Real systems expire keys after 24–48 h.
- **Side effects outside the database.** The order is idempotent, but the SMS is sent once per
  *successful* placement. When notifications move to Kafka (Phase 6–7), duplicates come back in
  another form: at-least-once delivery (scenario K3).
- **Payments.** Calling a payment provider is a side effect we can't roll back. Real payment APIs
  take an idempotency key for exactly this reason. Pass yours through.

## Discussion

1. Why must the key be claimed *before* reserving stock and not after?
2. What should the second tap return if the first is still in progress after 30 s: wait, 409, or

3. Is `GET /api/orders/{id}` idempotent? Is `POST /api/riders/{id}/location`? Which of our endpoints
