# 4.5 — Backfilling 1.5 million rows

> **Phase 4: changing the schema while the system is live.** Adding the column was instant. Filling
> it is the expensive part.

## Story

`orders.coupon_code` was added (nullable, instant). Every existing row needs a value, `'NONE'`.
Meanwhile customers keep ordering and **rating past deliveries**, single-row updates on old orders
(`POST /api/orders/{id}/rating`, added in `V5__order_rating.sql`).

## Run it

```bash
make load ID=4.5 MODE=broken    # one UPDATE, one transaction
make load ID=4.5 MODE=fixed     # 10,000 ids per transaction, 50 ms pause between batches
```

| | one transaction | batched (160 transactions) |
|---|---|---|
| Backfill took | 51 s | 69 s |
| Ratings OK | **72%** (p99 = 30 s timeout) | 100% (p99 140 ms) |
| Orders OK | **75%** (p95 5.8 s) | 100% |
| Dead rows right after | 1.59 M | 555k (autovacuum kept up) |

Batched is **slower in total and nobody notices it**. That's the right trade.

## Why one big transaction hurts

```sql
UPDATE orders SET coupon_code = 'NONE' WHERE coupon_code IS NULL;    -- 1.59M rows, 51 s
```

1. **Row locks pile up.** Every row it updates stays locked until the transaction commits. A customer
   rating an old order that was already updated waits for the *entire* backfill: up to 50 s, so the
   request times out. Those stuck requests hold threads, so orders suffer too (2.1 again).
2. **It's a long transaction.** For 51 s, VACUUM can't clean any row versions newer than its
   snapshot, anywhere in the database (watch **Postgres → Longest open transaction**).
3. **Dead rows.** In Postgres an `UPDATE` writes a new row version and leaves the old one dead.
   1.59 M dead rows appeared at once. **VACUUM** makes that space reusable but doesn't return it to the
   OS. Over the runs of this scenario the `orders` table grew from **352 MB to 788 MB**. Only `VACUUM
   FULL` or `pg_repack` shrinks it, and `VACUUM FULL` takes `ACCESS EXCLUSIVE` (4.1).
4. **A burst of WAL.** Every changed row is written to the write-ahead log, which replicas must replay.
   Phase 5 shows replicas falling behind.
5. **All or nothing.** If it fails at row 1,500,000, it rolls back 1,499,999 rows of work.

## How to batch properly

[`DbLabController.backfill`](../../services/core-service/src/main/java/dev/quickdrop/core/dblab/DbLabController.java):

```sql
UPDATE orders SET coupon_code = 'NONE'
WHERE id > :from AND id <= :from + 10000 AND coupon_code IS NULL;      -- commit, sleep 50 ms, next range
```

- **Walk the primary key in ranges.** Our first batched version used
  `WHERE id IN (SELECT id … WHERE coupon_code IS NULL LIMIT 10000)`. It looks simpler, but every batch
  rescans all the rows already done, so it got slower and slower and hadn't finished after 70 s.
- **Pause between batches** so autovacuum, replicas and normal traffic keep up. Watch dead rows and
  replica lag, and slow down if they grow.
- **Make it resumable.** Remember the last id done; a restarted job continues from there.
- **Make it idempotent.** `AND coupon_code IS NULL` means re-running a batch is harmless.
- **New rows**: set a column default first (or dual-write in the app), so the backfill has an end.
