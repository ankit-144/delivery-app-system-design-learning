# 3.3 — A price change two instances never hear about

> **Phase 3: scale out.** Caches are copies. With one instance there's one copy; with three there
> are three, and they disagree.

## Story

Product pages and order totals read product details through a cache, because prices change rarely
and are read constantly. Ten seconds into the test, product 7's price goes up by ₹50. The admin
request happens to hit core-1.

## Run it

```bash
make load ID=3.3 MODE=broken     # product-cache=local (a Caffeine cache in each JVM, 5-minute TTL)
```

60 product-page reads/s and 10 orders/s through nginx; the price changes at t = 10 s.

```
product page reads   after the change:   578 fresh,  1163 stale (66.8% stale)
orders charged       after the change:    99 fresh,   192 stale (66.0% stale)
```

Exactly two thirds: core-1 evicted its own entry when it made the change; core-2 and core-3 keep
the old price until their entries expire, five minutes later. **192 customers were charged the old
price.** Cheaper for them this time; next time it's a price *drop* and they're overcharged.

## Observe

- **Redis & scale-out → Product cache**: `local hit` stays high. The cache is "working" by its own
  metrics.
- Watch the request headers: `curl -si localhost:8080/api/products/7 | grep -E 'X-Served-By|pricePaise'`
  a few times during the run. The price depends on which instance you hit.

## Fixes

| Mode | Where the copy lives | After a change | Cost |
|---|---|---|---|
| `none` | no copy: Postgres every time | always correct | every read is a DB query |
| `local` | each JVM | stale on the other instances for up to the TTL | — |
| `redis` | one shared copy in Redis, deleted on change | correct (0 stale) | a network round trip per read |
| `two-tier` | each JVM **and** Redis; change → pub/sub message → every instance evicts | correct (0 stale) | one round trip per *miss*; needs pub/sub |

```bash
make load ID=3.3 MODE=redis     # 1741 fresh, 0 stale
make load ID=3.3 MODE=fixed     # two-tier: 1741 fresh, 0 stale
```

[`ProductCache.java`](../../services/core-service/src/main/java/dev/quickdrop/core/catalog/ProductCache.java)
implements all four. The invalidation path in two-tier mode:

```
admin PUT on core-1 → commit → DEL product:7 in Redis → PUBLISH product-invalidations "7"
                                                         ├─▶ core-1 evicts 7 from its local cache
                                                         ├─▶ core-2 evicts 7
                                                         └─▶ core-3 evicts 7
```

## Order of operations matters

Evict **after** the database commit
([`CatalogService.updatePrice`](../../services/core-service/src/main/java/dev/quickdrop/core/catalog/CatalogService.java)).
If you evict first, another request can reload the *old* value from the database before your commit,
and re-cache it.

Even after commit there's a classic race (a reader loads the old value, the writer commits and deletes
the key, then the reader writes its old value back into the cache). It's rare and short-lived with
TTLs, but real. Common mitigations: delete twice ("delayed double delete"), version stamps on cached
values, or Redis `SET … GET` patterns.

## Pub/sub is fire-and-forget

Redis pub/sub delivers a message only to subscribers connected **at that moment**. An instance that is
restarting, or briefly disconnected, misses the invalidation and keeps its stale copy until the TTL.
That's why two-tier caches still use a TTL as a safety net, and it's the preview for Redis
Streams (R6) and Kafka (Phase 6): messages that wait for the consumer.

## Discussion

1. Which data in a delivery app can be safely cached for minutes, which for seconds, and which never?
   (Product names? Prices? Stock levels? Rider positions?)
2. Why does `redis` mode still need a TTL if we delete on every change?
3. An order was charged a stale price. Whose responsibility is it to catch that: the cache, the order
   service, or the payment step?
