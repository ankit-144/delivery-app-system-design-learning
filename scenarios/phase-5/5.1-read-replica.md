# 5.1 — "I placed an order, but it's not in my orders"

> **Phase 5: scaling the database.** The first step when one Postgres isn't enough: move reads to a
> copy. The copy is always a little behind.

## Setup

```bash
make up PHASE=5     # adds postgres-replica (a streaming replica), its exporter, and two shards for 5.2+
```

The replica clones the primary with `pg_basebackup` and then **streams the write-ahead log (WAL)**:
every change made on the primary is shipped and replayed, typically within milliseconds
([`infra/postgres/replica/entrypoint.sh`](../../infra/postgres/replica/entrypoint.sh)).

```bash
docker exec qd-postgres-replica psql -U quickdrop quickdrop -c "SELECT pg_is_in_recovery()"     # t: read-only replica
docker exec qd-postgres psql -U quickdrop quickdrop -c "SELECT client_addr, state, replay_lag FROM pg_stat_replication"
```

The app now has two connection pools, `core-pool` (primary) and `replica-pool`, behind a routing
`DataSource` ([`DataSourceConfig`](../../services/core-service/src/main/java/dev/quickdrop/core/db/DataSourceConfig.java)).
The `read-routing` toggle decides where "My orders" reads go
([`ReadRouter`](../../services/core-service/src/main/java/dev/quickdrop/core/db/ReadRouter.java)).

## Story

"My orders" is the busiest read (2.3–2.5), so it moves to the replica. Under load the replica falls
**1.5 s** behind. The script sets that on purpose with `recovery_min_apply_delay`; real lag comes from write
bursts (4.5's backfill), long queries on the replica, or the network. Customers place an order and
immediately open "My orders".

## Run it

```bash
make load ID=5.1 MODE=primary   # reads on the primary
make load ID=5.1 MODE=broken    # reads on the replica
make load ID=5.1 MODE=fixed     # read-your-writes
```

| | Customers who didn't see the order they just placed | History reads on the replica |
|---|---|---|
| primary | 0 of 676 | 0 of 2,105 |
| **replica** | **676 of 676 (100%)** | 2,067 of 2,067 |
| **read-your-writes** | 0 of 676 | 1,482 of 2,229 (two thirds) |

Every single customer who ordered and looked was told, in effect, that their order didn't exist. Some
would order again (1.3 duplicates), some would call support.

## Why

The order was committed on the primary. The replica would replay it 1.5 s later. Reading from the replica
means reading **the past**. That's *eventual consistency*: the replica will agree with the primary, just
not yet. For most reads by most people that's fine. For the person who just made the change it's
visibly broken.

## Fix: read-your-writes

```
place order (primary) → mark "customer 4242 wrote" in Redis for 5 s
"My orders" for 4242  → marker present → read the primary
"My orders" for 9999  → no marker      → read the replica
```

Only the customer who just wrote pays for primary reads, and only briefly. Everyone else still reads the
replica: two thirds of history reads stayed off the primary in our run. The marker lives in Redis, so it
works whichever instance serves the next request.

Other ways to get there:

| Technique | How |
|---|---|
| Sticky to primary after a write | a cookie or session flag: "read from primary until <time>" |
| **LSN tracking** | after a write, remember `pg_current_wal_lsn()`; read from the replica only once `pg_last_wal_replay_lsn()` has passed it, otherwise primary (precise, no guessing) |
| Synchronous replication | `synchronous_commit = remote_apply`: the primary waits for the replica on every commit. No lag, but slower writes, and writes stall if the replica dies |
| Read critical things from the primary | e.g. payment status, stock. Only lists and browsing go to replicas |

## Watch the replica

- **Postgres dashboards**: `pg_replication_lag_seconds` from the replica's exporter (job `postgres-replica`).
- `make psql` on the primary: `SELECT * FROM pg_stat_replication;` (`write_lag`, `flush_lag`, `replay_lag`).
- The replica is read-only: `INSERT` fails with `cannot execute INSERT in a read-only transaction`.
