# 2.8 — Virtual threads: the limit moves

> **Phase 2: one box hits the wall.** Remove one bottleneck and the next one shows up.

## Story

After 2.1, someone reads that Java 21 has **virtual threads**: millions of cheap threads, so blocking
calls no longer exhaust a thread pool. One line of config:

```yaml
spring.threads.virtual.enabled: true
```

Does the slow vendor stop mattering?

## Run it

Virtual threads are a startup setting, so this scenario restarts core-1 in between:

```bash
make load ID=2.8 MODE=broken                 # 1. platform threads (default)
VIRTUAL_THREADS=true make rebuild S=core-1   # 2. restart with virtual threads
make load ID=2.8 MODE=broken                 # 3. same load, virtual threads
make load ID=2.8 MODE=in-tx                  # 4. vendor call inside the transaction (2.2's mistake)
make load ID=2.8 MODE=pinning                # 5. synchronized + blocking I/O
make rebuild S=core-1                        # back to platform threads
```

The script prints which kind of threads core-1 is running, so you can't mix up runs. 100 orders/s,
vendor latency 1 s.

| Run | Threads | Order p50 | Orders OK | Health OK | What ran out |
|---|---|---|---|---|---|
| 1. inline SMS | platform (50) | **12.3 s** | 100% (slowly) | 42% | Tomcat threads |
| 3. inline SMS | **virtual** | **1.04 s** | 100% | 100% | nothing: the wall is gone |
| 4. SMS inside the transaction | virtual | 5.0 s | **2.6%** | 100% | **DB connections**: 598 requests waiting for 10 |
| 5. `synchronized` + blocking I/O | virtual | **50 s** | 33% | **15%** | the one carrier thread |
| 5. same, for comparison | platform | 10 ms | 100% | 100% | nothing |

## Run 3: what virtual threads are

A platform thread is an operating-system thread (~1 MB stack, expensive to create and switch). Tomcat
keeps 50 of them. A **virtual thread** is a Java object: when it blocks on I/O (a socket read, a sleep),
the JVM unmounts it and runs another virtual thread on the same OS thread (a "carrier"). 100 orders
waiting on the vendor cost almost nothing. **Service saturation → JVM threads** showed only **24**
OS threads for 100+ requests in flight.

Run 3 is 2.1's scenario at higher load with no outage. For I/O-bound work, that's a big deal.

## Run 4: the next wall

Same virtual threads, but the SMS is sent inside the transaction (2.2's mistake):

```
api errors: db_pool_exhausted × 4,097
Hikari waiting threads: 598
```

With platform threads, Tomcat's 50-thread limit was accidentally **protecting** the connection pool:
at most 50 requests could be competing for 10 connections. Virtual threads removed that limit, and
600 requests piled onto 10 connections. **Removing a bottleneck exposes the next one**, and it may
fail more abruptly than the one you removed.

Virtual threads don't create database connections, CPU, vendor capacity or row locks. They only stop
*threads* from being the limit. Where you relied on the thread pool as a concurrency limit, you now need
an explicit one (a semaphore, a bulkhead, or a properly sized pool with a short timeout).

## Run 5: pinning

`inventory-reservation=synchronized` (1.1's JVM lock) does blocking work while holding a `synchronized`
lock. On **JDK 21**, a virtual thread that blocks inside `synchronized` can't unmount: it **pins** its
carrier thread. The carrier pool has one thread per CPU, and core-1 has **one CPU**.

So one virtual thread holding the store lock and waiting on the database blocks the only carrier.
Every other virtual thread, including the health check that has nothing to do with locks, waits.
With platform threads, the same code runs fine (100% OK, p50 10 ms).

How to spot pinning:

```bash
# JDK 21: log every pinned block with a stack trace (add to JAVA_TOOL_OPTIONS and restart)
-Djdk.tracePinnedThreads=full
```

Fixes: replace `synchronized` with `java.util.concurrent.locks.ReentrantLock` (virtual-thread friendly),
or upgrade to **JDK 24+**, where JEP 491 removed pinning for `synchronized`. Library code you don't
control (old JDBC drivers, some caches) can still pin, so test before switching.

## When to use virtual threads

- **Good fit**: I/O-bound request handling, lots of concurrent waiting on remote calls, code written in a
  simple blocking style.
- **No help**: CPU-bound work (2.6 wouldn't get faster: one CPU is one CPU).
- **Watch out**: anything that relied on the thread pool as a limit (connection pools, rate-limited
  vendors), `synchronized` + blocking on JDK < 24, and `ThreadLocal`-heavy code (millions of threads ×
  thread-locals = memory).
