# 2.2 — Calling the vendor inside the transaction

> **Phase 2: one box hits the wall.** Same slow vendor as 2.1, one line of code moved, a much
> worse outage.

## Story

A developer notices that SMS sometimes go out for orders that then fail. "Send the SMS inside the
transaction, so if the SMS fails, the order rolls back. Nice and consistent." The code moves the
`vendor.send()` call up a few lines, before the commit.

## Run it

```bash
make load ID=2.2 MODE=broken
```

Only **15 orders/s** this time (a quarter of 2.1), 40 browses/s, vendor latency 1 s,
`notification-mode=inline-in-tx`:

```
  stream        ok %    p50 ms    p95 ms    p99 ms
  order         93.3     26453     50068     51876
  browse        98.9     19923     45820     48644
  health        19.7     10000     10001     10001     ← 80% of health checks time out
  dropped iterations: 877
```

At a quarter of the traffic, it's a far worse outage than 2.1.

## Observe

**Service saturation → Connections: active / idle / waiting**

- `active` pinned at **10 / 10**; `waiting threads` climbing into the dozens.
- **Time to get a connection / time holding one**: `max held` ≈ **1 s**. A connection that should be
  borrowed for 3 ms is held for the whole vendor call.

**Postgres → Connections by state**

- **`idle in transaction`**: 10 connections in an open transaction, doing nothing on the database. The
  database is *waiting for the app*, which is waiting for the vendor.

**Overview → API errors**: `db_pool_exhausted`. Requests waited 5 s for a connection and gave up.

## Why

```
 BEGIN
   reserve stock        (row lock on inventory)
   insert order
   claim rider          (row lock on rider)
   call the SMS vendor  ← 1 second, holding: a pool connection + the stock row lock + the rider row lock
 COMMIT
```

- **The pool caps throughput.** 10 connections ÷ 1 s each = **at most 10 orders per second**. We send 15.
  The rest queue for a connection.
- **Everything else needs a connection too.** Browsing the catalogue is one fast query, but it waits
  in the same queue behind orders holding connections for a second each. That's why browse p50 is 20 s.
- **Locks are held for a second.** Every other order for the same product waits on that stock row
  (Phase 1's row locks, now held 300× longer).
- **The "consistency" is an illusion.** If the vendor accepts the SMS and *then* the commit fails, the
  customer got an SMS for an order that doesn't exist. A remote call can't take part in your database
  transaction. Phase 6 solves this properly with the *outbox* pattern.

## Fix

```bash
make load ID=2.2 MODE=fixed     # notification-mode = inline: call the vendor after commit
```

```
  order        100.0      1031      1054      1056     ← still waits for the vendor (1 s)…
  browse       100.0         1         1         1     ← …but nobody else does
  health       100.0         1         1         1
```

The connection goes back to the pool after ~3 ms. Orders are still slow (the vendor is still slow:
that's 2.1's problem), but the slowness no longer spreads.

> **The rule:** never hold a database transaction (or a lock) across a remote call. Do the remote
> call before `BEGIN` or after `COMMIT`.

The same trap in Spring is **Open Session In View** (`spring.jpa.open-in-view`, **on** by default!):
it keeps a connection for the whole HTTP request, including any slow call your controller makes.
QuickDrop turns it off in `application.yml`.

## The aftermath: abandoned work

When the broken run ended, the next run had to wait **~70 seconds** before core-1 answered a health
check. k6 had given up on hundreds of queued requests, but **the server didn't know**. It worked through
every one of them: reserving stock, assigning riders and sending SMS for customers who had long since
closed the app.

That's why deadlines need to *propagate*: a request the client has abandoned should stop doing work.
Real systems pass a deadline along with each request (gRPC does this built in) and check it before
expensive steps.

## What can still go wrong

- **Long transactions for other reasons**: a slow query, a big batch, a `sleep` someone left in for
  debugging. **Postgres → Longest open transaction** catches all of them.
- **Hikari leak detection** (`leakDetectionThreshold`) logs a stack trace when a connection is held
  longer than N seconds. It's cheap insurance.
