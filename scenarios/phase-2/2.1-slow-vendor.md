# 2.1 — A slow vendor eats every request thread

> **Phase 2: one box hits the wall.** The data is correct now. Traffic grows, and the question
> changes from "is it right?" to "which resource runs out first?"

## Story

Friday evening. The SMS vendor has a bad day: every send takes **1 second** instead of 100 ms.
Nothing is down; their API is just slow. Orders send the confirmation SMS **inline**, on the request
thread, after the order is committed.

Within a minute the whole app is slow, including pages that never send an SMS. Then the load
balancer's health checks start timing out.

## Run it

```bash
make load ID=2.1 MODE=broken
```

60 orders/s, 20 catalogue browses/s, 2 health checks/s for 60 s, vendor latency 1 s. What we measured:

```
  stream        ok %    p50 ms    p95 ms    p99 ms
  order        100.0      4327      6492      6756
  browse       100.0      3258      5456      5726     ← never calls the vendor
  health       100.0      3367      5438      5677     ← doesn't even touch the database
  dropped iterations: 268
```

## Observe

**Service saturation → Busy threads vs max**: pinned at **50 / 50**.

Little's law (from 0.1) predicts it: **60 orders/s × 1 s = 60 threads** needed just to wait for the
vendor. Tomcat has 50. Every thread is parked, so new requests (browse, health, everything) queue in
Tomcat's accept backlog until a thread frees up.

Other panels worth a look:

| Panel | What you see |
|---|---|
| Saturation → Vendor call latency | ~1 s: the cause |
| Saturation → JVM threads by state | a wall of `TIMED_WAITING`: threads waiting on a socket |
| Containers → core-1 CPU | low. **The app is idle and unresponsive at the same time.** |
| Saturation → Connections | Hikari mostly idle: the database isn't the problem |

That's the classic signature of a **thread-pool bottleneck**: CPU low, threads maxed, latency high
everywhere.

## Why it's worse than it looks

- **Health checks queue too.** In Kubernetes, a liveness probe with a 1–3 s timeout fails, and the pod
  gets restarted. A restart drops every in-flight request and sends the same traffic to fewer pods,
  which then fail too. A slow dependency has turned into a crash loop.
- **Pages that have nothing to do with SMS are slow.** One shared thread pool means one slow
  dependency can take down every endpoint. That's the case for **bulkheads**: separate pools per
  dependency, so one can't drain the others.

## Fix options, and what each one costs

### Option 1: a timeout

```bash
make load ID=2.1 MODE=timeout      # vendor-timeout-ms = 300
```

```
  order        100.0       303       305       315
  browse       100.0         1         1         1
  health       100.0         1         1         1
```

Threads are released after 300 ms, so the app is healthy again. The price is that **every SMS fails**:
we counted 2,264 failed sends in one run (**Overview → SMS sent by mode and result**). Customers are
fine with a missing "order confirmed" SMS. They wouldn't be fine with a missing OTP. Timeouts get
their own scenario (2.7).

### Option 2: send asynchronously, from an in-memory queue

```bash
make load ID=2.1 MODE=async        # notification-mode = async-memory
```

```
  order        100.0         2         3        13
  browse       100.0         0         1         1
```

Orders return in 2 ms. Problem solved? Look at **Service saturation → Vendor in-flight / async queue**:

- 4 sender threads × 1 SMS/s = **4 SMS per second out**; 60 per second come **in**.
- The queue grew to **2,237** messages in 40 s. Only 192 had been sent when the test ended. At 4/s the
  backlog takes ~9 minutes to drain, so customers get "order confirmed" ten minutes after the rider arrives.
- It lives **in the JVM's memory**. We restarted core-1 with 2,177 messages queued: all gone, and no
  log line says so.
- Unbounded, it grows until the heap runs out (**JVM heap** panel). `async-queue-capacity` bounds it,
  and then it drops messages instead.

**You didn't remove the queue, you moved it** from Tomcat's backlog, where it hurt everyone, to an
invisible in-memory list where it hurts only SMS. That's an improvement, but the real fix is a
**durable** queue that survives restarts and scales its consumers independently. That's Phase 6
(Kafka). Scenario 6.3 comes back to this exact queue.

### Option 3: more threads?

`make toggle NAME=tomcat-max-threads VALUE=200` during a broken run. It helps, until the next
resource runs out. Scenario 2.8 does this properly with virtual threads.

## What can still go wrong

- **Retries make it worse.** If the vendor is slow because it's overloaded, retrying failed sends
  doubles its load (scenario 8.3).
- **Async hides failures.** With inline sending, a broken vendor shows up as slow orders, which you
  notice. With async it shows up as a growing queue nobody looks at. **Alert on queue age**, not just size.
