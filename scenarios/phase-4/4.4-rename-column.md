# 4.4 — Renaming a column during a rolling deploy

> **Phase 4: changing the schema while the system is live.** With several instances, a deploy is
> never instant: for a while **old code and new code run against the same schema**.

## Story

`customers.phone` should become `customers.phone_number`. Orders read the phone to send the SMS,
and customers update their numbers. Three instances are running.

Each instance's `customer-phone-schema` toggle stands in for the app version it runs
([`CustomerDirectory`](../../services/core-service/src/main/java/dev/quickdrop/core/customer/CustomerDirectory.java)):

| Version | Reads | Writes |
|---|---|---|
| v1 | `phone` | `phone` |
| v1.5 | `phone` | `phone` **and** `phone_number` |
| v2 | `phone_number` | `phone` **and** `phone_number` |
| v3 | `phone_number` | `phone_number` |

## Run it

```bash
make up PHASE=3
make load ID=4.4 MODE=broken
make load ID=4.4 MODE=fixed
```

Traffic: 20 orders/s, 10 profile reads/s, 5 phone updates/s.

### Broken: "it's just a rename"

```
t+16s  rename-phone: done (7 ms)                ← instant migration
t+36s  the v3 deploy reaches every instance
  order      72.7% ok
  profile    72.7% ok
  update     72.9% ok
```

For 20 seconds every request touching a phone failed (`column "phone" does not exist`). Doing it the
other way round doesn't help: deploy v3 first and it fails, because `phone_number` doesn't exist yet.
**There's no order of "migrate, deploy" that works for a rename** when old and new code overlap.

### Fixed: expand → migrate → contract

```
t+6s   expand-phone: done (7 ms)                ADD COLUMN phone_number (nullable: instant)
t+6s   core-1 now runs v1.5                     write both, still read phone
t+9s   core-2 now runs v1.5
t+12s  core-3 now runs v1.5
t+15s  backfill-phone: done (57 ms)             copy phone → phone_number for every row
t+15s  phone vs phone_number drift after backfill: 0
t+18s  core-1 now runs v2                       read phone_number
…
t+27s  drift before switching writes: 0
t+27s  core-1 now runs v3                       write only phone_number
…
t+40s  contract-phone: done (6 ms)              DROP COLUMN phone
  order      100.0% ok
  profile    100.0% ok
  update     100.0% ok
```

At every moment, every running version finds the columns it needs. Each step is backward compatible
with the one before it.

## The rules

1. **Expand**: add the new thing alongside the old (new column, new table, new endpoint). Old code
   ignores it.
2. **Migrate**: write to both, backfill, switch reads, one deploy at a time.
3. **Contract**: remove the old thing only when **no running code** uses it, including old instances
   still draining, cron jobs, and the analytics team's reports.

### Two details that bite

**Backfill only after every instance writes both columns.** Our backfill is:

```sql
UPDATE customers SET phone_number = phone WHERE phone_number IS DISTINCT FROM phone;
```

not `WHERE phone_number IS NULL`. During the v1 → v1.5 rollout, a v1.5 instance can set both columns
and then a v1 instance changes `phone` alone. That row has a non-null but **stale** `phone_number`,
which an `IS NULL` backfill would skip. `IS DISTINCT FROM` catches it, and the drift check confirms 0.

**Every step is a separate deploy.** In this scenario the steps are seconds apart. In real life they're
days apart, and each one must be safe to roll back to the previous version, which is what keeping both
columns buys you.

A database trigger can keep the two columns in sync instead of dual writes in the app. That's handy
when other systems also write the table.
