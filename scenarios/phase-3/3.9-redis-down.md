# 3.9 — Redis goes away

> **Phase 3: scale out.** We added Redis to fix five problems. Now it's a single point of failure for
> all five.

## Story

Everything Redis-backed is on: the Redis stock lock (3.2), sliding-window rate limits (3.5), the
Redis product cache (3.3), Redis GEO rider matching (3.4), and cached best sellers (3.8). Fifteen
seconds in, Redis **stops answering**: Toxiproxy turns the connection into a black hole for 30 s, then
restores it.

Traffic: 20 orders/s, 5 OTPs/s, 30 product reads/s, 10 best-seller reads/s.

## Run it: four modes, one lesson each

```bash
make load ID=3.9 MODE=broken    # redis-failure-mode=fail
make load ID=3.9 MODE=degrade   # fallbacks, no circuit breaker
make load ID=3.9 MODE=breaker   # fallbacks + circuit breaker
make load ID=3.9 MODE=fixed     # fallbacks + circuit breaker + cheap fallbacks
```

| Mode | Orders OK | Order p50 | Order p95 | Products OK | Best sellers OK | OTPs OK |
|---|---|---|---|---|---|---|
| fail | 52% | 342 ms | 1.0 s | 52% | 52% | 52% |
| degrade | 85% | 721 ms | **20.6 s** | 99% | 99% | 72% |
| + breaker | 76% | 4.6 s | 17.9 s | 93% | 93% | 62% |
| **+ cheap fallbacks** | **100%** | **8 ms** | **106 ms** | **100%** | **100%** | 49% (on purpose) |

## Lesson 1: a dependency outage becomes your outage (`fail`)

Every feature that touches Redis fails while Redis is gone: about half the run, so about half the
requests. At least it fails *fast*: Lettuce's command timeout is **1 s** here (`REDIS_TIMEOUT_MS`).
**Lettuce's default is 60 seconds**, which would hold a thread for a full minute on every Redis call (2.7
again).

`/actuator/health` stays green the whole time, because the Redis health indicator is disabled on
purpose. If it weren't, the load balancer would take *every* instance out of rotation because of a
cache outage, turning a partial outage into a total one.

## Lesson 2: fallbacks, decided per feature (`degrade`)

| Feature | When Redis is down | Why |
|---|---|---|
| Stock lock | `SELECT … FOR UPDATE` in Postgres | slower, but still correct |
| Product cache | read Postgres | cheap primary-key lookups |
| Rider GEO | `db-nearby` query | 2.6's indexed query |
| Rate limit: orders | **fail open** (allow) | a few extra orders are better than no orders |
| Rate limit: OTP | **fail closed** (deny) | each OTP costs money; an unlimited OTP endpoint is what attackers wait for |
| Best sellers | compute it | …see lesson 4 |

The fallbacks work (144 orders used the DB lock; the rate limiter allowed 244 orders and denied 78 OTPs),
but **p95 is 20 seconds**. Every Redis call still waits its full 1 s timeout *before* falling back, and
an order makes several Redis calls. Threads pile up just like 2.1.

## Lesson 3: stop asking (`breaker`)

A **circuit breaker** ([`GuardedRedisTemplate`](../../services/core-service/src/main/java/dev/quickdrop/core/redis/GuardedRedisTemplate.java),
Resilience4j) wraps every Redis command:

```
 CLOSED ──(≥50% of the last 20 calls failed)──▶ OPEN ──(5 s)──▶ HALF_OPEN ──(3 trial calls ok)──▶ CLOSED
   calls go to Redis                              fail instantly          a few calls test Redis
```

Once open, fallbacks run in microseconds (1,908 calls short-circuited in one run). And yet it got
**worse**: orders dropped to 76%. Look at **Postgres CPU: 2.0 of 2**.

## Lesson 4: the fallback took down the backup

The best-sellers fallback runs the 0.6 CPU-second query **on every request**. Ten per second is 6 CPUs
of work for a 2-CPU database. Before, the cache absorbed that load. With the cache gone, the fallback
sends all of it to Postgres, and Postgres falls over, taking orders with it (they need the same
database). The breaker just made the fallback arrive *faster*.

This pattern causes real outages: the cache was quietly load-bearing, and the "safe" fallback is a
denial-of-service attack on your own database.

## Fix: degrade cheaply (`fixed`)

`bestsellers-fallback=last-known`: when Redis is unreachable, each instance serves the last best-seller
list **it** served (or an empty widget), and never runs the expensive query. Result: orders 100% at
p50 8 ms, products 100%, best sellers 100% (a few seconds stale). OTPs are refused during the outage
(fail closed), which is exactly what we decided.

Principles:

1. **Timeouts on every call**, short ones (lesson 1).
2. **Decide the fallback per feature**, with the business: open or closed, stale or empty (lesson 2).
3. **Circuit breakers** so a dead dependency costs nothing per request (lesson 3).
4. **A fallback must be cheaper than the thing it replaces**, or limited (bulkhead, rate limit) so it
   can't overwhelm what it falls back to (lesson 4).
5. **Test it.** None of these fallbacks matter until Redis actually dies. Game days (8.5) exist for this.

## Discussion

1. Which features would you let fail entirely during a Redis outage, and which must keep working?
2. Why is "fail open" right for order rate limits and wrong for OTP rate limits?
3. The breaker opens per instance. With 30 instances, how many failed calls happen before every
   instance has stopped calling Redis?
4. When Redis comes back, every cache is empty. What happens to Postgres in the next 10 seconds?
