# 6.1 — A synchronous call chain

> **Phase 6: notifications, from a sync call to Kafka.** Notifications move into their own service.
> Splitting the code is easy; the hard part is what happens *between* the services.

## Setup

```bash
make up PHASE=6     # Kafka (KRaft, no ZooKeeper), Kafka UI (localhost:8085), notification-1/2, kafka-exporter
```

Sending SMS now lives in [`notification-service`](../../services/notification-service). Two instances share
the work. In this scenario core calls it over HTTP and waits (`notification-mode=http`), and it calls the vendor
and waits (`delivery-mode=sync`):

```
 customer → nginx → core ──HTTP──▶ notification-service ──HTTP──▶ SMS vendor (2 s today)
                     ▲  waits                ▲  waits
```

## Run it

```bash
make load ID=6.1 MODE=broken
```

80 orders/s, 20 browses/s, 2 health checks/s; the vendor takes 2 s.

```
  stream        ok %    p50 ms    p95 ms    p99 ms
  order        100.0      2940      4325      4513
  browse       100.0       915      2345      2507     ← never sends an SMS
  health       100.0       900      2387      2499     ← doesn't even touch a database
  dropped iterations: 141
```

## What happened

**Latency adds up along the chain.** Every order waits for notification-service, which waits for the vendor.
The vendor's 2 s *is* our checkout latency.

**Capacity multiplies down the chain.** 80 orders/s × ~2 s ≈ 160 requests in flight, over 3 core instances ≈
53 each, and Tomcat has 50 threads per instance. Once those are busy, everything queues: browsing and health
checks too. It's 2.1 again, now across a network boundary, which makes it harder to see. The core
dashboards show threads maxed and CPU idle, and the cause is two hops away.

(At 30 orders/s the same chain "only" adds 2 s to every order: still a terrible checkout, just not an outage.)

## Why chains are fragile

- **Availability multiplies.** If each hop is up 99.9% of the time, a chain of 3 is up 99.7%. Every
  synchronous dependency you add makes your service *less* available than its weakest dependency.
- **Latency adds, and so do tails.** The p99 of a chain is worse than the sum of the p99s, because the
  slow responses at each hop don't line up.
- **One slow service ties up threads in everything that calls it.** This is how a slow SMS vendor takes down
  checkout.

## What to do about it

1. **Protect the caller**: timeouts, circuit breakers, bulkheads (6.2).
2. **Don't wait for things the customer doesn't need right now.** The order is confirmed when it's in the
   database. The SMS can go out a second later. Make the call **asynchronous**: a queue between core and
   notification-service (6.3 → 6.5).

2. Why are the browse and health requests slow when they never call notification-service?
