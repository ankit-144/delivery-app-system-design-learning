# 5.3 — How requests find their shard

> **Phase 5: scaling the database.** A code walkthrough. No load test, just curl and the source.

## The pieces

| Class | Job |
|---|---|
| [`Shards`](../../services/core-service/src/main/java/dev/quickdrop/core/sharding/Shards.java) | one small connection pool per shard database (`SHARD_URLS`) |
| [`ShardRouter`](../../services/core-service/src/main/java/dev/quickdrop/core/sharding/ShardRouter.java) | `shardFor(customer, city)` according to `shard-key` |
| [`SnowflakeIds`](../../services/core-service/src/main/java/dev/quickdrop/core/sharding/SnowflakeIds.java) | ids that encode their shard (5.4) |

| [`ShardingAdminController`](../../services/core-service/src/main/java/dev/quickdrop/core/sharding/ShardingAdminController.java) | per-shard migrations, status, resharding maths |

## Follow one write

```bash
curl -s -X POST localhost:8080/api/sharded/orders -H 'Content-Type: application/json' \
     -d '{"customerId": 3, "storeId": 4, "totalPaise": 25000}'
```

1. Look up the store's city: store 4 → Mumbai (city 2).
2. `ShardRouter.shardFor(customer 3, city 2)`:
   - `shard-key=city` → `(2 - 1) % 2` = **shard 1**
   - `shard-key=customer` → `murmur(3) % 2`
3. Generate an id (`id-strategy`), insert into **that shard only**, and return `{"id": "...", "shard": 1}`.

## Follow one read

```bash
curl -s localhost:8080/api/sharded/customers/3/orders | python3 -m json.tool | head -20
```

The answer includes `shardsQueried` and `millisPerShard`. With `shard-key=city` you'll see 2 shards and
two timings: a scatter-gather, run in parallel on virtual threads and merged by `created_at`. With
`shard-key=customer`, one.

## Router in the app vs elsewhere

Our router lives inside the application (a *client-side* router). The alternatives:

| Where the routing lives | Examples | Trade-off |
|---|---|---|
| In the app (this lab) | custom code, Spring's `AbstractRoutingDataSource` | simple, but every service must embed the same logic |
| A proxy in front of the shards | Vitess (MySQL), Citus coordinator, PgDog | apps see "one database"; the proxy is new infrastructure |
| The database itself | CockroachDB, YugabyteDB, Spanner (distributed SQL) | transparent sharding, distributed transactions; different performance model |
| A lookup service ("directory") | a table mapping key → shard | any placement, easy moves; one more hop and one more thing to keep available |

Phase 5's routing `DataSource` for the read replica (5.1) is the same idea one level down: one logical
data source, several physical ones, a decision per connection.
