# 2.3 — "Just make the connection pool bigger"

> **Phase 2: one box hits the wall.** The most common reaction to `Connection is not available`
> errors, and what it really does.

## Story

"My orders" is slow and requests fail with `db_pool_exhausted`. The dashboard shows Hikari's
`waiting threads` climbing. The obvious fix: raise `maximum-pool-size` from 10 to 40. Someone
goes further and makes it 120.

(The real cause is a missing index; that's scenario 2.4. Here we pretend nobody has looked yet.)

## Run it

```bash
make load ID=2.3 MODE=pool10
make load ID=2.3 MODE=pool40
make load ID=2.3 MODE=pool120
```

40 "my orders" requests/s against 1.4M orders with no index, 10 orders/s, 2 health checks/s.
`db-pool-size` is changed **live** through Hikari's management bean. `tomcat-max-threads` is
raised to 200 so the thread pool isn't the first limit hit.

What we measured:

| | pool 10 | pool 40 | pool 120 |
|---|---|---|---|
| "My orders" served | 14.7 /s | 17.1 /s | 24.1 /s |
| "My orders" p99 | 12.1 s | 15.3 s | **25.8 s** |
| **Orders** succeeding | **7%** | 34% | 58% |
| Postgres CPU | 2.0 of 2 | 2.0 of 2 | 2.0 of 2 |
| Postgres connections | 14 | 49 | **107** (limit: 100) |
| Postgres memory | 563 MB | 720 MB | **827 MB** (limit: 1 GB) |

And in the Postgres log at 120:

```
FATAL:  sorry, too many clients already
```

## What the numbers say

**1. The database CPU was pinned at 2.0 in every run.** A connection is permission to use the
database, not extra database. Every request is a full table scan, and no pool size changes the
amount of scanning.

**2. Throughput did go up, more than you might expect.** Postgres has a trick called *synchronized
scans*: a sequential scan that starts while another scan of the same table is running joins it
midway, so they share the reads. With 40–100 concurrent scans of `orders`, each one gets cheaper. With
fewer connections, each query also gets parallel workers, and those carry overhead. That's a real
effect, but it's specific to this workload. Most CPU-bound databases get *slower* with too many
concurrent queries (context switching, lock contention, cache thrashing).

**3. Latency got worse for the requests that did finish.** p99 doubled. More concurrent queries share
the same 2 CPUs, so each one takes longer.

**4. You can run out of connections on the database side.** Postgres allows 100 (`max_connections`).
Each connection is a separate OS process with its own memory: Postgres grew from 563 to 827 MB, close to
its 1 GB container limit. At 120 the pool simply couldn't open more: `too many clients`.

**5. One slow endpoint starved another.** The surprising row is **Orders succeeding: 7%** at pool 10.
"My orders" requests grabbed every connection in the shared pool, and order placement, the thing that
makes money, timed out waiting behind them. The bigger pools "helped" orders only by having more
room for both.

## Now multiply by instances

Phase 3 runs **three** core instances. Pool 40 × 3 = 120 connections, already over `max_connections`.
Every instance you add takes connections from the same fixed budget:

```
max_connections ≥ instances × pool size + admin + migrations + replicas + headroom
```

This is why large deployments put a connection pooler (PgBouncer) between apps and Postgres, and why
pool sizes are usually *small*: a common starting point is `cores × 2 + effective spindles`, about 5–10
for our 2-CPU database.

## The real fixes

- **Make the query cheap**: scenario 2.4, one index, p50 from 20 s to 2 ms.
- **Isolate workloads (bulkheads)**: give order placement its own pool (or its own instance), so a slow
  read endpoint can't starve checkout. Phase 5 sends history reads to a **read replica**.
- **Limit concurrency on the expensive endpoint**: better to reject 30% of "my orders" requests
  quickly than to time out 93% of orders (load shedding, 8.4).
