# 3.6 — A scheduled job that runs on every instance

> **Phase 3: scale out.** `@Scheduled` means "on every instance". Nobody thinks about that until the
> second instance exists.

## Story

When no rider is free, an order waits in `PENDING_RIDER`. Every 2 seconds a background job
([`PendingRiderJob`](../../services/core-service/src/main/java/dev/quickdrop/core/order/PendingRiderJob.java))
retries those orders. It was written for one instance. Now core-1, core-2 and core-3 all run it, at
the same moment, on the same pending orders.

## Run it

```bash
make load ID=3.6 MODE=broken
```

Only 50 riders online near store 1, 20 orders/s, deliveries take 5 s, so there's always a queue of
pending orders. After 60 s:

```
FAIL rider_ghost_busy       violations=29
```

**29 of the 50 riders are ghosts**: marked BUSY for an order that has a different rider. They will
never be freed. More leak away every round, and the fleet slowly disappears.

## Why

```
 core-1 job                               core-2 job
 SELECT pending orders → [#881, #882, …]  SELECT pending orders → [#881, #882, …]   (same list)
 #881: claim rider 17 (conditional ✓)     #881: claim rider 23 (conditional ✓)       (different riders, both free)
 order #881.rider = 17, COMMIT
                                          order #881.rider = 23, COMMIT              (overwrites)
```

Rider 17 is BUSY with `current_order_id = 881`, but order 881 now says rider 23. When 881 is delivered,
the simulator frees rider 23. Nobody ever frees rider 17.

The conditional `UPDATE` from 1.2 doesn't help here: it stops two orders taking the same *rider*,
not one order taking two riders. **Every invariant needs its own guard.**

## Fixes

```bash
make load ID=3.6 MODE=redis    # scheduler-lock=redis       → 0 ghost riders
make load ID=3.6 MODE=fixed    # scheduler-lock=skip-locked → 0 ghost riders
```

### Option 1: only one instance runs the job (a scheduler lock)

```java
lock.tryOnce("job:pending-rider", Duration.ofMillis(1900))   // SET NX PX: one winner per round
    .ifPresent(lease -> { retryEach(); lock.release(lease); });
```

That's what the library [ShedLock](https://github.com/lukas-krecan/ShedLock) does (with Redis, a
database table, or ZooKeeper). It's simple, but it brings back 3.2's question: what if the run lasts
longer than the lock?

### Option 2: every instance runs, and they claim different work

```sql
SELECT id FROM orders
WHERE status = 'PENDING_RIDER' AND created_at < now() - interval '2 seconds'
ORDER BY created_at LIMIT 1
FOR UPDATE SKIP LOCKED
```

`FOR UPDATE` locks the row until the transaction commits; `SKIP LOCKED` makes other instances skip
locked rows instead of waiting. Each pending order is processed by exactly one instance, and three
instances get through the queue three times faster. **This is how to build a job queue on Postgres**,
and Phase 6 uses it before moving to Kafka.

Note that [`DeliverySimulator`](../../services/core-service/src/main/java/dev/quickdrop/core/order/DeliverySimulator.java)
used `SKIP LOCKED` from day one, which is why it never caused trouble on three instances.

### Option 3: run jobs somewhere else

A dedicated worker process (one replica), a Kubernetes CronJob, or a job system (Quartz in cluster
mode, db-scheduler, JobRunr). That keeps the web instances free of background work.

## Watch out for jobs that are "harmless" on every instance

The invariant checker runs on all three instances too. It's read-only, so it's correct, but it puts
the same aggregate queries on Postgres three times every 5 seconds. Scale to 30 instances and your
*monitoring* becomes your biggest database workload.
