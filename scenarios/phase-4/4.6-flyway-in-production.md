# 4.6 — Flyway in a multi-instance deploy

> **Phase 4: changing the schema while the system is live.** Where and when migrations run is a
> design decision.

QuickDrop runs Flyway **inside each app instance at startup** (Spring Boot's default). That's simple
for one instance. Here's what happens with three, and what most teams do instead.

## Experiment: two instances start with a new, slow migration

We added a temporary `V6__lab_slow_migration.sql` containing `SELECT pg_sleep(15);`, rebuilt, and
started core-1 and core-2 at the same moment:

```
core-2  00:21:06.854  Migrating schema "public" to version "6 - lab slow migration"
core-2  00:21:21.941  Successfully applied 1 migration … (execution time 00:15.009s)
core-1  00:21:06.838  Successfully validated 6 migrations
        … 16 seconds of nothing …
core-1  00:21:22.938  Current version of schema "public": 6 — Schema "public" is up to date.
```

Flyway takes a **Postgres advisory lock** before migrating, so only one instance runs migrations;
the other waits, then sees the work done. **Correct**, but notice:

- **Both instances spent 22 s starting.** A migration that takes 10 minutes means instances that take 10
  minutes to start. Kubernetes' liveness probe kills them halfway, they restart, start the migration
  again, and you get a crash loop with a half-applied migration.
- **Startup now depends on the database being migratable.** A migration that can't get its lock (4.1)
  blocks every new instance.

(To try it yourself: add the file, `make up PHASE=3`, read `make logs S=core-1`. Then **remove the file
and its row**: `DELETE FROM flyway_schema_history WHERE version = '6';`, otherwise Flyway refuses to
start because an applied migration has disappeared.)

## Better: migrations as a separate step

```
 deploy pipeline:   1. run migrations (a one-off job: flyway migrate)   ← fails? stop here, nothing deployed
                    2. roll out the new app version
                    3. (later release) contract migrations
```

- Migrations run once, from one place, with its own timeouts and logs.
- The app starts fast and doesn't need DDL permissions (separate DB users: `app` can read/write,
  `migrator` can alter).
- In Kubernetes: an init container, a pre-deploy Job, or a Helm hook. Spring Boot:
  `spring.flyway.enabled=false` in the app and the Flyway CLI or Maven plugin in the pipeline.

## Checklist for a production migration

| Question | Scenario |
|---|---|
| Does it take `ACCESS EXCLUSIVE`? Is `lock_timeout` set? | 4.1 |
| Does it build an index? `CONCURRENTLY`, outside a transaction? Check for invalid indexes after | 4.2 |
| Does it rewrite the table or scan it under a lock? | 4.3 |
| Is it backward compatible with the version currently running? | 4.4 |
| Does it update many rows? Batched, resumable, throttled? | 4.5 |
| Has it been tried on a production-sized copy, and timed? | all of them |
| Can the *previous* app version run against the *new* schema (for rollback)? | 4.4 |

## Flyway rules that matter

- **Never edit an applied migration** (checksum mismatch, see 0.3). Fix forward with a new version.
- **Versions must increase.** A teammate's `V7` merged after your `V8` was applied is "ignored" unless
  `outOfOrder=true`. Agree on a numbering scheme (timestamps work well: `V20261011_1200__…`).
- **One change per migration, especially for non-transactional ones** (`CREATE INDEX CONCURRENTLY`), so
  a failure leaves a clear state.
- **Repeatable migrations** (`R__…`) re-run whenever they change. Useful for views and functions, never for
  data.
