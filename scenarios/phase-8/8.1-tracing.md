# 8.1 — Where did the time go? Distributed tracing

> **Phase 8: operating it.** Metrics tell you *that* something is slow. A trace tells you *where*:
> one request, followed through every service, query and queue it touched.

## Run it

```bash
make up PHASE=8                 # starts Tempo and turns tracing on in every service
make load ID=8.1 MODE=broken    # outbox-trace-context=drop
make load ID=8.1 MODE=fixed     # outbox-trace-context=propagate
```

Customers say order confirmations "sometimes take ages". Orders go through the outbox (6.6) → Kafka →
notification-service → SMS vendor, and 5% of vendor sends take 2 s. The script places 20 orders/s for 45 s, then
asks Tempo what it received:

| | Order traces | ...that continue to the SMS vendor | Orphan traces starting at the Kafka send |
|---|---|---|---|
| `drop` | 901 | **0** | **901** |
| `propagate` | 901 | **901** | **0** |

With `drop` you can still find slow SMS sends (`{ resource.service.name = "vendor-mock" && duration > 1s }`), but
not which order they belonged to, nor how long the customer actually waited. With `propagate`, the slowest
order trace of our run told the whole story:

```
    0 ms     8.5 ms  core-service          POST /api/orders   (+ 14 SQL spans, 11.7 ms in total)
    8 ms     0.5 ms  core-service          outbox relay → notifications send
 2957 ms             ── 2.95 s waiting in Kafka: the consumers were busy with other slow vendor calls ──
 2957 ms  2002 ms    notification-service  notifications receive → POST to vendor
 2959 ms  2001 ms    vendor-mock           POST /v1/sms                       ← the 5% slow sends
```

The customer waited 5 s for the confirmation. The vendor explains 2 s of it. The other 3 s were the message waiting
behind slow sends on the same partitions (6.8's head-of-line blocking), invisible in any single service's metrics.

## What a trace is

Every service creates **spans** (one unit of work: an HTTP request, a SQL query, a Kafka send) and passes the
**trace context** (`traceparent: 00-<trace id>-<span id>-01`, the W3C standard) to whatever it calls next:
in an HTTP header, in Kafka record headers. Tempo assembles spans with the same trace id into one tree:

```
 core-service           POST /api/orders ─────────────────────── 182 ms
 core-service             connection / query × 12  (SQL)          ~1 ms each
 core-service           outbox relay ─────────  (~200 ms later, another thread)
 core-service             notifications send   (Kafka)
 notification-service       notifications receive ───────────
 notification-service         POST → vendor
 vendor-mock                    POST /v1/sms ─────────  2,000 ms   ← there it is
```

This repo uses Spring Boot's Micrometer Tracing with the OpenTelemetry bridge, exporting over OTLP to Tempo. Nothing
in the business code creates spans: Spring instruments HTTP servers and clients, Spring Kafka instruments
producers and consumers (`observation-enabled: true`), and
[datasource-micrometer](https://github.com/jdbc-observations/datasource-micrometer) wraps JDBC.

## Where traces break: async boundaries

Context travels with a call. Anything that **stores work and does it later** drops it, unless you carry it
yourself:

- **The outbox** (6.6): the order commits a row, a scheduler publishes it 200 ms later on another thread, often on
  another instance. With `drop`, the trace ends at the INSERT and the Kafka message starts an unrelated trace:
  you can see that *some* SMS took 2 s, but not *whose order* it was.
- **The fix** ([`Outbox`](../../services/core-service/src/main/java/dev/quickdrop/core/notification/Outbox.java),
  migration V7): store the request's `traceparent` in the outbox row. The relay opens a span with that parent before
  publishing, and Kafka's header propagation does the rest.
- The same applies to thread pools (`@Async`, executors), in-memory queues (6.3), database queues (6.4), and
  batch jobs. For executors, Spring's `ContextPropagatingTaskDecorator` copies the context onto the worker thread;
  for anything that goes through storage, you carry `traceparent` yourself, as the outbox does.

## Logs and metrics, joined to traces

- **Logs**: every log line written while handling a request carries `[traceId-spanId]`. In Grafana → Explore →
  Loki, the trace id is a link to Tempo; in Tempo, *Logs for this span* jumps back.
- **Exemplars**: latency histograms carry the trace id of sample requests. On Overview → *p99 latency* (and
  Operating → *Checkout latency*), the dots are exemplars. Click one to open that request.
- **Service graph**: Tempo derives who-calls-whom and per-edge latency from spans (Explore → Tempo → Service
  graph, or Operating → *Service graph*).

## TraceQL to try

```
{ resource.service.name = "vendor-mock" && duration > 1s }                       slow vendor calls
{ rootName = "http post /api/orders" && name = "notifications receive" }          orders whose SMS you can follow
{ rootName = "notifications send" }                                               orphans (MODE=broken)
{ name = "connection" && duration > 100ms }                                       waiting for a DB connection (2.2)
{ rootName = "http post /api/orders" && name = "query" } | select(span."jdbc.query[0]")   SQL per order
```

## The cost of tracing

- **Sampling**: we keep 100% of traces (`TRACING_SAMPLING=1.0`). At production volume that's expensive, so services
  keep 1–10% (*head sampling*: decided at the first service, passed along in `traceparent`), or send everything
  to a collector that keeps errors and slow traces and samples the rest (*tail sampling*).
- **Noise**: background jobs would create a trace every 200 ms per instance. `management.observations.enable.[tasks.scheduled]=false`
  and [`TracingNoiseFilter`](../../libs/quickdrop-common/src/main/java/dev/quickdrop/common/observability/TracingNoiseFilter.java)
  keep SQL and Redis spans only inside requests and messages, and skip Prometheus scrapes. Our first version of the
  filter checked `parent != null`; a dropped parent is a no-op placeholder, not null, so every background query
  still became its own trace.
- **Load**: during the 8.3 retry storm, Tempo's service-graph processor dropped spans. Tracing infrastructure needs
  capacity planning too.
- **Long traces**: Tempo considers a trace finished after `trace_idle_period` without new spans. With the 10 s
  default, an order's late SMS spans were stored as a separate piece, and searches combining both halves missed
  half the orders (docs/FAILURE_TRACKER.md). We use 60 s, so a trace becomes searchable a minute after its last span.
